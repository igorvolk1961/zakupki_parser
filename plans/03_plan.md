# Этап 3. Парсинг по ОКПД2 + клиентская фильтрация словами + per-profile оценки (R1, R9) — детальный план

> Источник: мастер-план (этап 3, MVP), трекер `plans/plan.md`.
> Требование заказчика (R9): ключевые слова НЕ передаются на площадку; серверная
> фильтрация — только по кодам ОКПД2 (+ отдельный обход «без кода»); позитивные и
> негативные слова применяются клиентски сразу после получения списка и ДО записи в БД.
> Результаты одинаковы для пользователей с одинаковым ОКПД2-фильтром (обходы общие).

## Задачи (по порядку)

### 3.1. Движок парсера: серверный поиск ТОЛЬКО по ОКПД2 (R9)
- Убрать подстановку `profile.keywords` в `search_criteria` (orchestrator): поиск строится
  на `search_criteria.okpd_codes` (+ глобальные критерии) без слов.
- Убрать перебор `keywords_one_at_a_time` (B2B/fabrikant) и обход «по словам» — слова
  не участвуют в серверном запросе.
- Обход «без кода»: отдельный проход без фильтра ОКПД2 при наличии хотя бы одного
  позитивного слова в профиле; иначе — пропуск с записью в лог. По умолчанию
  ВЫКЛЮЧЕН; включается глобальным флагом `config_service.yaml -> search_criteria.no_code_search`
  (решение заказчика: параметр площадки `no_code_search` удалён).

### 3.2. Клиентская пост-фильтрация словами до записи в БД (R9)
- Новый модуль `parser/filtering.py`: матчинг выражений файла профиля
  (`data/profile.md`, стандартный синтаксис `слов*`/`~N`):
  - `(фраза* фраза*)~N` — не более N слов между токенами;
  - `слов*` — усечённое слово/все токены фразы;
  - точная фраза/слово (без `*`/`~`).
- Позитивные слова: совпадение хотя бы одного (пустой список → нет фильтра).
- Слова-исключения: отсутствие всех (любое совпадение → отброс).
- Нестандартная эвристика `keyword_context_regexes` **удалена** (миграция 1.31):
  её функции покрываются стандартным синтаксисом файла.
- Подключение в `_process_list_record` ДО записи: `keyword_context_required`/
  `exclusion_words_present` вливаются в этот шаг (поведение становится обязательным).

### 3.3. Per-user контекст и оценки
- Оценки (auto-Fit) пишутся в `procurement_evaluations` под активный профиль сервис-аккаунта (уже с Этапа 1);
  ручная корректировка — вне MVP. Обходы (площадка × ОКПД2) общие; per-user
  планировщик по профилям — развитие в рамках пост-MVP (Этап 4C/10), данные поддерживают.

### 3.4. Тесты
- Unit: `filtering.py` (regex, ~N, `*`, точные фразы, минус-слова); запрос к ЭТП без слов;
  обход «без кода» (skip без позитивных слов с логом).
- Обновить устаревшие тесты `test_orchestrator_keywords.py` (серверные слова) на
  клиентскую фильтрацию.
- Прогон: `uv run pytest tests/unit -q`, integration при DSN, `ruff`, `mypy`,
  `zp check-config`.

## Заглушки
- `no_code_search` — глобальный конфиг-флаг `config_service.yaml -> search_criteria`
  (по умолчанию выкл: обход «без кода» пропускается с логом при наличии позитивных слов).
- Кэш обходов (R4) и очередь воркеров (4C) — пост-MVP (этапы 4/10).

## Критерии приёмки
1. В запросах к ЭТП нет ключевых слов (только ОКПД2/«без кода»).
2. Позитивные/негативные слова фильтруют запись ДО записи в БД.
3. Обход «без кода» пропускается при отсутствии позитивных слов (лог).
4. unit без регрессий, ruff/mypy/check-config чисто.
