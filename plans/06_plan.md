# Этап 6. Условия отчётных полей и сайты-источники (проверка кодов ФККО по компетенциям поставщика)

> Источник: требование заказчика — проверять, что коды ФККО закупки входят в
> компетенции (лицензию) поставщика. Пример заказчика:
> https://onlineecology.com/org/ooo-ekopattern (4723 кода, 237 страниц пагинации).
> Цель этапа: обобщённый механизм без адаптеров под конкретные сайты.
> Адаптеры (в т.ч. генерируемые агентом) — следующий этап; связка «код →
> вид работ» на этом этапе — по тексту между кодами (п. 4.3), для источников,
> где она так не видна, — следующий этап.

## Контекст (по коду)

- Отчётное поле профиля — `profiles.report_fields` (JSONB):
  `{id, name, hint, type, unit, expected_value, blocking}`
  (`storage/db/profile.py:118`, `api/app/schemas.py:487`).
- `expected_value` — свободный текст; совпадение оценивает LLM в том же вызове,
  что и извлечение (`pipeline/prompts/field_extract_user.md`,
  `report_fields.py:151` → `match: bool | None`).
- Вердикт: `blocking=True` и `match=False` — стоп-условие
  (`pipeline/verdict.py`); Excel — `routes/procurements.py:800-815`;
  UI — `clients.js:1287-1340` (редактор поля), `procurements.js:858` (карточка).
- Типы полей: `string | number | date | boolean` (`FIELD_TYPES`).
- Сайт поставщика: `profiles.website_url`; `profile_source.py` скачивает ОДНУ
  страницу (httpx, SSRF-защита `_ensure_public_host`), текст обрезается до
  8000 символов, ничего не сохраняется.
- S3/MinIO: `scoring_common/tz/object_cache.py` — best-effort кэш, по умолчанию
  выключен (`TZ_CACHE_ENABLED`); ошибки не пробрасываются. В тестах флаг
  утекает из `.env` и даёт флаки (реальный MinIO отвечает на мок-URL).
- Отчётное поле извлекается LLM по top-k фрагментам ТЗ
  (`report_field_top_k`) — длинный список (таблица кодов) может не
  поместиться целиком; извлечённые значения отдельно от `match` не хранятся
  (пересчёт условия = повторный LLM).
- Браузер (Playwright) уже есть в API-процессе: `zakupki_parser/browser/manager.py`,
  используется `parser/by_url.py` для живой подгрузки закупки по URL.
- Пример заказчика: пагинация рисуется JS из JSON (подписи «Страница N»),
  в исходном HTML ссылок на страницы нет → сбор возможен только браузером.

## Решения

1. **Условие вместо `expected_value`.** Поле получает
   `condition: {op, value_kind, value, near?}` + отдельный флаг `blocking`
   (условие без блокировки — информативный ✓/✗, как сейчас).
2. **Условие по возможности проверяется кодом, без LLM.** LLM только
   извлекает значение из ТЗ. Исключение — оператор `llm` («соответствует
   по смыслу»): в него мигрируют существующие `expected_value`.
3. **URL в условии — текст сайта целиком, собранный по всем страницам
   пагинации**, хранится в файловом хранилище (S3). Ключ — нормализованный
   URL; один и тот же URL (в т.ч. `website_url` профиля) — одна запись,
   собирается один раз.
4. **Совпадение значения с текстом — по шаблону, построенному из самого
   значения** (п. 4.2): пользователь regex не пишет, структура кодов не
   хардкодится; для текстовых значений — по основам слов.
5. **«Рядом» = между значениями**: уточнения ищутся от найденного
   значения до следующего значения той же формы — и в источнике, и в ТЗ.
   В ТЗ это даёт связку «код → требуемые виды работ»; в источнике —
   проверку «у этого кода есть эти виды работ» (п. 4.3). Уточнения —
   значения другого отчётного поля (из ТЗ) или постоянные слова
   пользователя. Слова сравниваются по основе без окончания (`утилизац*`),
   разные суффиксы не сводятся.
6. **Список из ТЗ: LLM даёт образцы, код проверяет и дополняет** (п. 4.4).
   Значения делятся на коды и текст (п. 4.2): коды — строгий шаблон и
   дополнение по форме; текст — поиск по основам слов; дополнение по месту
   в тексте — для любых значений.
7. **Хранилище S3 обязательно** для всех сервисов (и текст ТЗ, и сайты):
   флаг `TZ_CACHE_ENABLED` удаляется (п. 2.1).
8. **Условие пересчитывается без LLM**: извлечённые значения хранятся,
   проверка условия — чистый код (п. 4.5).
9. **Длительные операции показывают прогресс** (п. 7.1).
10. **Отдельной опции аккаунта нет**: условия работают там, где работает
    RAG-анализ.
11. **«Не проверено» ≠ «не соответствует».** Если сбор сайта не завершён,
   значение не извлечено или сайт недоступен — `match=None` +
   `check_status` с причиной; такое поле не блокирует, но показывается
   серым «не проверено» в карточке и Excel.

## 1. Модель условия

```jsonc
"condition": {
  "op": "all_in",            // см. таблицу
  "value_kind": "url",       // scalar | list | url
  "value": "https://onlineecology.com/org/ooo-ekopattern",
  "near": {                  // необязательно; только для value_kind=url
    "source": "field",       // field | words
    "field_id": "f_activities",       // для source=field: поле «Виды работ»
    "words": [],                       // для source=words: ["утилиз*", ...]
    "mode": "all",           // any | all
    "window": 300,           // ±символов — только для текстовых значений
    "max_window": 2000       // предел окна «до следующего значения»
  }
}
```

| op | смысл | value_kind | типы поля |
|---|---|---|---|
| `eq`, `ne` | равно / не равно | scalar | все |
| `gt`, `gte`, `lt`, `lte` | сравнение | scalar | number, date |
| `in` / `not_in` | значение ТЗ есть / нет в списке | list, url | string, number, list* |
| `all_in` | все значения ТЗ есть в списке/тексте | list, url | list |
| `any_in` | хотя бы одно есть | list, url | list |
| `none_in` | ни одного нет | list, url | list |
| `contains` | значение ТЗ содержит подстроку | scalar | string |
| `llm` | «соответствует по смыслу» (прежнее поведение) | scalar | все |

\* для поля `list` оператор `in` = `all_in`.

- Новый тип поля **`list`** (список значений): промпт `field_extract_list.md`,
  LLM возвращает `value: [..]` со всеми найденными значениями, без
  дедупликации; нормализация/дедуп — в коде.
- `near` разрешён только при `value_kind=url` (для scalar/list окрестности нет).
- Для `list`-значений в условии допускается ввод через запятую/перенос
  строки и загрузка .txt/.csv (одна колонка).

## 2. Хранилище сайтов-источников

**Таблица `site_sources`** (liquibase `db.changelog-1.68.yaml`):

| колонка | тип | назначение |
|---|---|---|
| `id` | bigserial | |
| `url_norm` | text unique | нормализованный URL (схема/хост в нижний регистр, без `#`, без `utm_*`, без завершающего `/`) |
| `url` | text | как ввёл пользователь |
| `status` | text | `pending` / `running` / `complete` / `incomplete` / `failed` |
| `stop_reason` | text | `no_next` / `repeat` / `no_change` / `page_limit` / `size_limit` / `time_limit` / `error` / `nav_failed` |
| `pages` | int | собрано страниц |
| `text_bytes` | int | размер текста |
| `s3_key` | text | ключ объекта с текстом |
| `fetched_at`, `started_at` | timestamptz | |
| `progress` | jsonb | `{pages, bytes, current_url, mode, updated_at}` — обновляется после каждой страницы |
| `cancel_requested` | bool | кнопка «Остановить» → итог `incomplete`, `stop_reason=cancelled` |
| `error` | text | для `failed` |

- Текст — в S3: модуль `scoring_common/sources/store.py`, бакет
  `SOURCE_STORE_BUCKET`, ошибки **пробрасываются** (данные, а не ускорение).
- Формат объекта: текст страниц, разделённый маркером
  `\n\n=== page N: <url> ===\n\n` (для отладки и превью; при поиске
  маркеры не мешают — шаблоны значений не пересекают `\n`).
  Промежуточный текст дописывается частями (каждые 20 страниц), чтобы
  прерванный сбор не терял собранное.
- `complete` = пагинация закончилась сама (`no_next`/`repeat`/`no_change`);
  `incomplete` = упёрлись в лимит или не удалось перейти на найденную
  следующую страницу. Проверки по `incomplete`-источнику дают «не проверено»
  для отрицательного результата (найденное значение — найдено, отсутствие не
  доказано).
- Обновление: TTL (`site_sources.ttl_days`, по умолчанию 30) + ручная кнопка.
  Устаревший источник используется, пока идёт пересбор.

### 2.1 S3 обязателен

- `TZ_CACHE_ENABLED` удаляется: `S3CacheSettings.enabled` убрать,
  `endpoint_url`/ключи — обязательные; при старте каждого сервиса
  (API, parser, indexing, scoring, analysis) — проверка доступа к бакетам
  (`head_bucket`), без S3 сервис не стартует с понятной ошибкой.
- `object_cache` для текста ТЗ остаётся best-effort на уровне **операций**
  (сбой чтения/записи не прерывает извлечение), но выключить его нельзя.
- docker-compose: MinIO + создание бакетов — обязательная часть стека;
  `.env.example`, `docs/DEPLOY.md` обновить.
- Тесты: фикстура по умолчанию подменяет S3-клиент хранилищем в памяти
  (`InMemoryS3`), реальный MinIO — только в явных интеграционных тестах.
  Заодно устраняет утечку `TZ_CACHE_ENABLED` из `.env` в `test_api.py`.

## 3. Сбор сайта (краулер пагинации)

Модуль `zakupki_parser/sources/crawler.py`, Playwright (существующий
`browser/manager.py`), запускается фоновой задачей API-процесса.

**Поиск «следующей страницы»** (по порядку, первый сработавший):
1. `a[rel=next]`, `link[rel=next]` (переход по href);
2. элемент с `aria-label`/`title`/текстом, совпадающим с
   `след|next|далее|›|»|→|страница {N+1}|стр\. {N+1}` (клик);
3. числовой ряд ссылок/кнопок пагинации: элемент с текстом `N+1` внутри
   контейнера, где есть ≥2 соседних числа (клик);
4. `показать (ещё|больше)|загрузить ещё|load more` (клик, накопление);
5. параметр `page|p|PAGEN_\d+|pageIndex` в URL текущей страницы
   (инкремент);
6. бесконечная прокрутка: прокрутка вниз, пока растёт `scrollHeight`.

**Признак конца (без счётчика результатов):** после каждого шага —
отпечаток основного текста (текст `body` без `header/footer/nav`, хэш).
Остановка: нет кандидата «следующая» / кандидат disabled (`no_next`);
отпечаток уже встречался (`repeat`); текст не изменился после клика/прокрутки
за таймаут (`no_change`). Для режимов 4 и 6 («накопление») сравнивается
прирост текста, сохраняется только новая часть.

**Удаление шапки/подвала сайта.** После сбора — общий префикс и общий
суффикс (построчно) текстов всех страниц (при ≥ 3 страницах) удаляются из
каждой страницы: это оформление, а не данные (меню, панель фильтров,
подвал). Удаляется только непрерывный блок в начале/конце страницы —
повторяющиеся строки внутри данных («Сбор (1)» в каждой строке таблицы)
не трогаются. Исходный текст первой страницы сохраняется отдельно (для
`profile_from_url` и отладки).

**Лимиты** (`config_service.yaml → site_sources`): `max_pages` (500),
`max_text_mb` (30), `page_timeout_s` (20), `total_timeout_min` (20),
`delay_ms` (300–800, случайная), `concurrency` (1 сбор на хост, 2 всего).

**Безопасность:** та же SSRF-проверка, что в `profile_source.py`
(вынести `_ensure_public_host` в общий модуль), + перехват запросов
браузера (`page.route`) с отказом на непубличные адреса; только http/https.

**Жизненный цикл задачи:** `pending` → `running` → итог. При старте API
«зависшие» `running` старше `total_timeout_min` переводятся в `failed`
(`error="прервано перезапуском"`).

## 4. Проверка условия

Модуль `scoring_common/conditions.py` (чистый код, без I/O) — используется
analysis_service; текст источника подгружается через `sources/store.py`
(в памяти процесса — LRU по `s3_key`, тексты крупные).

### 4.1 Скалярные/списочные операторы
Нормализация перед сравнением: строки — `casefold`, схлопывание пробелов,
`ё→е`; числа — `float`; даты — ISO. Списки — множества нормализованных
значений.

### 4.2 Поиск значения в тексте: коды и текст
Значение (из ТЗ, из списка условия, слово «рядом») ищется в тексте одним из
двух способов — по **виду значения**:

- **код** — есть цифры и цифр ≥ 50% от букв+цифр (`1 11 010 21 49 2`,
  `62.01.11`, `ГОСТ 12.1.004`, `A-123-BX`);
- **текст** — всё остальное.

Вид определяется автоматически для каждого значения; в редакторе поля —
переключатель «вид значений: авто / коды / текст» (по умолчанию «авто»).

**Код — строгий шаблон:**
- берутся только буквы/цифры значения в исходном порядке;
- между ними — `[ .\-/]?` (необязательный одиночный разделитель, без `\n`);
- границы: `(?<![0-9A-Za-zА-Яа-я])…(?![0-9A-Za-zА-Яа-я])`.

`1 11 010 21 49 2` находит `11101021492`, `1 11 010 21 49 2`,
`1-11-010-21-49-2`; не находит `111010214921`. Значение короче 3 символов —
ошибка валидации условия (слишком много ложных совпадений).

**Текст — по основам слов:**
- значение и текст нормализуются: `casefold`, `ё→е`;
- значение разбивается на слова, каждое приводится к основе (Snowball,
  русский/английский; новая зависимость `snowballstemmer`);
- совпадение — те же основы **в том же порядке**, каждая — начало слова
  текста, между словами только пробелы/знаки препинания (без `\n`);
- «отходы бумаги» находит «Отход бумаги», «отходов бумаги»; не находит
  «бумажные отходы» (синонимы/перестановки — только оператор `llm`).

Индексы для поиска (нормализованный текст, позиции слов) строятся один раз
на документ/источник и кэшируются в памяти процесса.

### 4.3 «Рядом»: уточнения между значениями

**Окно — от найденного значения до следующего значения той же формы.**
- Форма выводится из значений ТЗ так же, как в п. 4.4 (цифра → `\d`,
  буква → `[A-Za-zА-Яа-я]`, разделители — как в образце). Для границы окна
  форма допустима и у кодов без разделителей: посторонний номер (телефон)
  лишь укорачивает окно, ложного «есть» он не даёт.
- Окно — только вперёд (вид работ в таблице идёт после кода; текст перед
  кодом относится к предыдущей строке).
- **Конец окна** — ближайшее из:
  1. начало следующего значения той же формы;
  2. граница страницы источника (маркер `=== page N ===`) или граница
     документа ТЗ (файла). Окно никогда не переходит на следующую
     страницу/файл: иначе последнее значение страницы захватит подвал и
     шапку следующей (на onlineecology в шапке — панель фильтра со всеми
     видами работ → ложное «есть рядом»);
  3. `start + 1.5 × L`, где `L` — медиана расстояний между соседними
     значениями **той же страницы/документа** (типичная длина «строки»);
     на странице < 3 значений — медиана по всему источнику/ТЗ;
  4. `near.max_window` (2000 символов) — абсолютный предел.
- Так определяется окно **последнего значения** каждой страницы/документа
  (п. 1 отсутствует → решают пп. 2–4), и так же обрезается окно
  значения, за которым идёт длинный посторонний текст.
- Значение — единственное во всём тексте (медиану не посчитать) — окно
  ±`near.window` (300), как у текстовых значений.
- Для текстовых значений (форма не выводится) — окно ±`near.window`
  символов (300).

**Откуда уточнения** (`near.source`):
- **`field`** (основной случай) — значения другого отчётного поля той же
  закупки, извлечённые LLM из ТЗ (поле «Виды работ»:
  `["транспортирование", "утилизации"]`).
- **`words`** (запасной) — постоянные слова пользователя.

**Связка «значение → уточнения» в ТЗ — тем же окном.** Для каждого
значения из ТЗ (код ФККО) в тексте ТЗ берётся окно до следующего кода
(п. выше), в нём ищутся слова уточнений:
- нашлись — значение требует **именно их** (код A → утилизация,
  код B → транспортирование);
- не нашлись (в ТЗ общая фраза «транспортирование и утилизация отходов
  по перечню») — значение требует **все** уточнения поля.

Результат — `requirements: {"1 11 010 21 49 2": ["утилизации"], ...}` в
значении поля; хранится вместе со списком, пересчёт без LLM (п. 4.5).

**Проверка по источнику.** Для каждого значения из ТЗ — его окна в тексте
источника; значение подтверждено, если хотя бы в одном окне найдены **все**
требуемые ему уточнения (`mode=all`, по умолчанию) или хоть одно
(`mode=any`). Для `all_in` — в `missing` попадают значения с причиной:
`нет в источнике` / `нет рядом: утилизации`.

**Сопоставление слов — отбрасывается только окончание.**
- Слово уточнения → основа (Snowball) + `*`: «утилизации» → `утилизац*`;
  совпадение — слово окна, начинающееся с основы (регистр и `ё/е` не
  важны). Уточнение из нескольких слов — в окне должны быть все его слова.
- Разные суффиксы не сводятся: `утилизац*` не находит «утилизировать».
  На этом этапе этим пренебрегаем.
- Короткие основы дают ложные совпадения (`сбор*` ↔ «сборка») — видно в
  `near_matches: {"утилизац*": ["утилизация"], ...}`, отображается в
  карточке.
- Ручные слова (`source=words`) — тот же синтаксис: UI предлагает основу
  (`POST /api/conditions/stem`), пользователь может её править; `*` только
  в конце, основа ≥ 3 букв; хранится утверждённый шаблон.

В «Проверить» (п. 6) — совпавшие словоформы с частотами в источнике
(`утилизац* → утилизация 184`).

Ограничение: в таблице, где виды работ вынесены в заголовки колонок
(не повторяются в строке), окно их не содержит → ✗ «нет рядом». Такие
источники — следующий этап (адаптеры).

### 4.4 Список значений из ТЗ (поле типа `list`)
LLM надёжно даёт образцы, но не полный список: видит только top-k
фрагментов, может пропустить строки таблицы или вернуть несуществующее
значение. Поэтому после LLM:

1. **Проверка присутствия** — каждое значение ищется в полном тексте
   документов закупки (п. 4.2):
   - код не найден → **отбрасывается** (`rejected_values`, для отладки);
   - текст не найден → **остаётся**, помечается «не подтверждено»
     (`unconfirmed_values`): у текста вероятнее расхождение формулировки,
     чем выдумка LLM. Условие учитывает его как обычное значение, UI
     показывает пометку.
2. **Дополнение по месту** (любые значения): списки в ТЗ идут блоком
   (таблица, перечисление). По позициям подтверждённых значений в полном
   тексте берётся участок от первого до последнего вхождения
   ± `list_span_margin` (1500 символов), не длиннее `list_span_max`
   (30 000; длиннее — участок вокруг самого плотного скопления). Если
   участок не покрыт фрагментами, которые LLM уже видела, — повторный
   вызов LLM только на этом участке, результат объединяется и снова
   проходит п. 1. Не более одного дополнительного вызова на поле.
3. **Дополнение по форме** (только коды): из подтверждённых кодов с
   разделителями выводится форма: цифра → `\d`, буква → `[A-Za-zА-Яа-я]`,
   серии схлопываются (`1 11 010 21 49 2` → `\d \d{2} \d{3} \d{2} \d{2} \d`),
   разделитель — как в образце. Полный текст сканируется по форме, найденное
   добавляется. Коды без разделителей (`11101021492`) форму не порождают:
   `\d{11}` ловит телефоны и прочие номера.
4. Дедупликация — по канонической форме (коды — только буквы/цифры; текст —
   последовательность основ).
5. Результат: `value` — итоговый список, `value_sources` —
   `{llm: n, span: k, pattern: m}`, `unconfirmed_values`, `rejected_values`.
6. Если список пуст — `check_status=not_found_in_tz`.

В редакторе поля — чекбокс «дополнять список по тексту ТЗ» (пп. 2–3),
включён по умолчанию.

### 4.5 Хранение значений и пересчёт без LLM
Извлечённые значения уже сохраняются в `rag_report.fields[]`. Проверка
условия выносится из `ReportFieldExtractor` в отдельный шаг
`evaluate_conditions(fields_values, profile_fields, sources)`, который:
- вызывается сразу после извлечения (как сейчас);
- вызывается **отдельно**, без LLM, по событиям: источник перешёл в
  `complete`/`incomplete`; условие поля изменено (оператор, значение,
  «рядом», «блокирует»). Затрагиваются закупки профиля(ей), у которых поле
  с этим условием; пересчитываются `match`, `check_status` и вердикт
  (авто-отклонение/его снятие — как при обычном анализе).
- Изменение `name`/`hint`/`type` поля по-прежнему требует повторного
  извлечения (LLM).

### 4.6 Результат
`ReportFieldValue` расширяется:
- `condition` — копия условия (для фронта/Excel);
- `check_status`: `ok` / `not_found_in_tz` / `source_pending` /
  `source_incomplete` / `source_failed` / `llm_failed`;
- `missing: list[str]` — для `all_in`: значения ТЗ, не найденные в
  источнике (показывается пользователю, обрезается до 50);
- `match` — как сейчас (`None`, если `check_status != ok`, кроме случая
  «найдено в неполном источнике» → `True`).

`expected_value` из `ReportFieldValue` удаляется после миграции.

## 7. UI

Редактор отчётного поля (`clients.js`, `zakupki.html`):
- тип поля: + «список»;
- «Условие»: оператор (список фильтруется по типу поля) → значение:
  переключатель «значение / список / сайт»;
  - список: textarea + загрузка файла;
  - сайт: URL + бейдж статуса сбора (собирается N стр. / готово N стр.,
    дата / не завершён: причина / ошибка) + «Обновить»;
- «Рядом должны быть» (только для «сайт»): «значения поля [Виды работ ▼]»
  (по умолчанию) или «слова» (ввод слова → чип с редактируемой основой
  `утилизац*`); любое/все; окно (по умолчанию 300). Ссылка на поле —
  только на поле того же профиля, не на само себя; удаление поля, на
  которое ссылаются, — с предупреждением;
- «Блокирует» — чекбокс, как сейчас;
- «Проверить»: ввести пример значения → результат + фрагмент текста с
  подсветкой совпадения и слов «рядом».

### 7.1 Прогресс длительных операций

| операция | где видно | что показывается |
|---|---|---|
| сбор сайта | редактор поля, форма профиля (`website_url`), список источников | «Собрано 57 стр. · 1,2 МБ · 1:34 · режим: кнопка „Страница N“», текущий URL, «Остановить»; итог: «Готово: 237 стр., пагинация закончилась» / «Не завершён: лимит страниц (500)» / ошибка |
| пересчёт условий | профиль, баннер над списком закупок | «Пересчёт условий: 120 / 430 закупок» |
| повторное извлечение (LLM) | профиль | как сейчас для пересборки + счётчик |
| заполнение профиля по URL | форма профиля | этапы: «загрузка страницы → разбор LLM» (сейчас — просто ожидание) |

Опрос статуса — раз в 2 с, пока операция активна (общий helper в
`static/js`, остановка опроса при уходе со страницы). В карточке закупки
при несобранном источнике — «⏳ источник собирается (57 стр.)», а не
«не проверено».

### 7.2 Карточка закупки и Excel

Карточка закупки (`procurements.js`) и Excel (`procurements.py`):

## 8. Тесты

Быстрые (по умолчанию):
- вид значения: авто-определение (коды/текст/смешанные), ручное
  переопределение.
- поиск текста по основам: падежи находятся, перестановки/синонимы — нет,
  границы слов, `ё/е`, регистр.
- список из ТЗ: несуществующий код отбрасывается, ненайденный текст
  остаётся с пометкой; дополнение по месту (таблица из 50 наименований,
  LLM вернула 5 → повторный вызов на участке, не более одного); дополнение
  по форме (коды); сплошные цифры не обобщаются; телефоны рядом с кодами
  не попадают в список.
- `evaluate_conditions` без LLM: смена условия/готовность источника меняет
  `match` и вердикт; LLM-мок не вызывается.
- старт сервиса без S3 → понятная ошибка; фикстура `InMemoryS3`.
- окно «до следующего значения»: граница по форме, только вперёд,
  текстовые значения — ±N; посторонний номер укорачивает окно;
  последнее значение страницы не переходит маркер страницы/границу
  файла; предел `1.5 × медиана` (по странице, фолбэк — по источнику);
  единственное значение — ±N; шапка следующей страницы с видами работ не
  даёт ложного «есть».
- удаление шапки/подвала: общий префикс/суффикс страниц убирается,
  повторяющиеся строки внутри данных остаются; < 3 страниц — не трогается.
- связка в ТЗ: код с видом работ в своей строке → только он; без —
  все значения поля; `requirements` пересчитывается без LLM.
- проверка по источнику: `all`/`any`, причины в `missing`,
  `near_matches`; `утилизац*` находит «Утилизация», не «утилизировать».
- шаблоны со `*`: подсказка основы, `*` только в конце, минимум 3 буквы,
  слово без `*` — целиком; частоты совпавших словоформ в «Проверить».
- `conditions.py`: каждый оператор × тип; шаблон значения (разделители,
  границы, отказ на коротких значениях); «рядом» (any/all, окно, начала слов,
  регистр); итоговые `check_status`/`match` для неполного/несобранного
  источника.
- миграция `expected_value` → `condition` (SQL на тестовой БД + импорт JSON).
- `report_fields.py`: тип `list`, новые поля результата; `verdict.py`:
  блокирует только `ok`+`match=False`.
- API: CRUD источников, дедуп по `url_norm`, SSRF-отказы, `conditions/test`.

Медленные (`@pytest.mark.slow`, запуск только по согласованию):
- краулер на локальных HTML-фикстурах: `rel=next`; числовая пагинация;
  JS-кнопка «Страница N» (как у onlineecology); «показать ещё»;
  бесконечная прокрутка; последняя страница, повторяющая себя; пагинация
  есть, но переход не работает → `incomplete`; `max_pages`.
- ручная проверка на onlineecology.com/org/ooo-ekopattern: собрано 237 стр.,
  `complete`, в тексте 4723 кода.

   (`docs/c4/db-schema.md`, ER-модель системного анализа) — `report_fields`,
   `site_sources`; глоссарий — отчётное поле, условие, сайт-источник,
   уточнения «рядом» (вместо упразднённых вопросов к ТЗ). Проверка на
   примере заказчика — реальный сбор и 4720 кодов лицензии ЭКОПАТТЕРН.
6. ✅ Уровни барьеров и возврат BR-03 (решение пользователя: мягкий барьер
   снижает P(win); опыт — всегда по BR-03, в профиле только «учитывать или
   нет»):
   - флаг `blocking` → уровень `severity`: `block` — жёсткий (авто-отклонение),
     `soft` — мягкий (`verdict.soft_reasons`), нет — только отчёт; и у полей,
     и у категорий требований (`profiles.requirement_severity`, опыт —
     `br03`/`off`); миграция 1.70 переводит профили и сохранённые отчёты;
   - BR-03 (`scoring_common.verdict`): способ подтверждения опыта из
     `data.confirmation`/`ref_2571`, иначе по формулировке; площадка без
     опыта `platform` в профиле — жёсткий, сканы/реестр/не распознан —
     мягкий, критерии оценки — не барьер;
   - P(win) = `p_win_base` × `soft_pwin_factor`^N (конфиг `scoring`, 0,7),
     score пересчитывается из составляющих — API при записи pwin/margin,
     анализа, пересчёта условий; правка опыта профиля запускает пересчёт;
   - UI: списки уровней вместо чекбоксов, карточка/Excel — мягкие янтарным,
     P(win) модели → итоговое.

Шаг 0 — первым (от него зависит 2). Шаги 1 и 2 независимы.
