> Тип: план документационных работ (код не затрагивается).
> Статусы задач: ⬜ запланировано · 🟡 в работе · ✅ выполнено.
> Приоритеты: P0 — блокирующее (пустые/битые артефакты, противоречия), P1 — значимое
> (отсутствующие артефакты, требуемые заказчиком), P2 — улучшения и поддержание.
> **Статус: ✅ ВЫПОЛНЕНО (2026-08-24)** — все задачи фаз 0–5 закрыты; открытые вопросы
> подтверждены решением заказчика. См. README-индекс `docs/system_analysis/README.md`.

## 1. Цель и принципы

Привести набор артефактов `docs/system_analysis/` к состоянию, при котором он:

1. **Согласован с реализацией** — не противоречит фактическому коду, схеме БД,
   конфигурации и уже пройденным этапам перестройки (этапы 0–3 выполнены);
2. **Полон** — закрыты явные пробелы (пустые файлы, отсутствующие артефакты:
   бэклог, матрица трассируемости, функциональные требования, реестр рисков);
3. **Трассируем** — любое требование (US/BR/NFR/FR) можно проследить до ER-модели,
   диаграмм, бэклога и этапа реализации;
4. **Используется как источник истины** для разработки этапов 4–10 и приёмочных
   испытаний MVP.

План рассматривается как **требования разработчика**: каждый пункт имеет проверяемый
критерий приёмки и ссылку на фактическое состояние кода, чтобы доработка не «плыла»
от реальности. План не изменяет исходный код `src/` — только `docs/system_analysis/`
и (по согласованию) `specification.md`, `plans/`, `README.md`.

Факты, обязательные к учёту при доработке артефактов:

- Каскад **Fit → P(win) → Margin** реализован (`scoring_transport` + Redis-очереди +
  `scoring_service`/`pwin_service`/`margin_service`); автокаскад отключён, P(win)/Margin —
  **on-demand** по запросу тендеролога.
- Уведомления — **постадийные** (`notify_min_fit_score`/`pwin`/`margin`, каналы Telegram/MAX/webhook).
- Экспорт — только **CSV** (XLSX — этап 8).
- Анализ ТЗ — **RAG по вопросам профиля** (вердикты `absolute/soft/no_stop_condition`);
  формализованных маркеров по BR-03/04 нет.
- Авторизация: регистрация/логин есть; trial/frozen/удаление (`users.status`,
  `trial_end_date`) — этап 6; `subscriptions`/`audit_log`/`procedure_categories` —
  заглушки/отсутствуют.
- Оценки пишутся в `procurement_evaluations` (auto-Fit) под **активный профиль**;
  ручная корректировка — пост-MVP.

## 6. Критерии готовности

1. Нет пустых файлов в `docs/system_analysis/`.
2. Каждый US/BR/NFR имеет ID и связан с этапом и статусом (матрица SA-1.3).
3. Бэклог SA-1.2 полон и согласован с `plans/plan.md` и §14.1.
4. Артефакты не противоречат коду: проверочный чек-лист — «прочитать артефакт → найти
   реализацию (файл/эндпоинт/миграцию) → отметить статус»; расхождений нет.
5. Для MVP-скоупа собран чек-лист приёмки (SA-1.6), по которому можно провести испытания.
6. README-индекс (SA-2.6) описывает набор и правила его поддержки (SA-5.x).
