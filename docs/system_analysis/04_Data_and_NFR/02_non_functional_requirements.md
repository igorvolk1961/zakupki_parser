# Нефункциональные требования (NFR)

## 1. Экономика и Стоимость (Cost Efficiency)
**Заказчик**: Product Owner

| ID         | Требование                     | Метрика / Ограничение|
| :--------- | :----------------------------- | :------------------- |
| NFR-COST-1 | Стоимость глубокого анализа    | Прямые затраты на LLM-токены при глубоком анализе ТЗ (RAG + LLM) не должны превышать $0.05 (или эквивалент в рублях) на одну закупку. |
| NFR-COST-2 | Экономия на повторном парсинге | Стоимость повторной обработки закупки, чьи метаданные не изменились на ЭТП, должна быть равна "$0" (использование кэша/хэшей, BR-01).
| NFR-COST-3 | Лимиты токенов (RAG)           | Размер промпта для LLM при анализе ТЗ жестко ограничен (например, 4000 токенов). RAG-пайплайн обязан отсекать нерелевантные чанки до отправки в модель.


## 2. Производительность и Масштабируемость (Performance & Scalability)
**Заказчик**: DevOps / SRE, Тендеролог (UX)

| ID         | Требование                     | Метрика / Ограничение |
| :--------- | :----------------------------- |---------------------- |
| NFR-PERF-1 | Отклик API (UI)                | Время отклика API на стандартные запросы (список закупок, карточка) не должно превышать 200 мс (95-й перцентиль).
| NFR-PERF-2 | Асинхронность тяжелых задач    | Запуск глубокого анализа ТЗ или парсинга не должен блокировать UI. API обязан возвращать статус 202 Accepted менее чем за 50 мс, а фоновая обработка идти через очередь (RabbitMQ/Redis).
| NFR-PERF-3 | Горизонтальное масштабирование | Компоненты парсинга и скоринга (Воркеры) должны быть stateless. Добавление новых инстансов воркеров должно линейно увеличивать пропускную способность системы без изменения кода. |


## 3. Безопасность и Compliance (Security & Legal)
**Заказчик**: Юрист, Тендеролог (Конфиденциальность)

| ID        | Требование                          | Метрика / Ограничение |
| :-------- | :---------------------------------- | --------------------- |
| NFR-SEC-1 | Изоляция данных (Multi-tenancy)     | Утечка данных между пользователями (user_id) недопустима. 100% запросов к БД на чтение/запись приватных данных должны автоматически фильтроваться по user_id на уровне ORM/БД (BR-07). |
| NFR-SEC-2 | Управление секретами                | "API-ключи LLM, токены Telegram/Max, пароли БД "никогда не хранятся в коде или репозитории. Только через переменные окружения (.env) или Secrets Manager.
| NFR-SEC-3 | Защита персональных данных (152-ФЗ) | Система не должна сохранять в БД персональные данные физлиц (ФИО, телефоны), если они случайно встречаются в тексте ТЗ. Они должны маскироваться или удаляться на этапе парсинга.
| NFR-SEC-4 | Юридический дисклеймер              | Отказ от ответственности («Результаты носят информационный характер...») должен отображаться в UI при просмотре карточки и в подвале любого экспортируемого отчета (XLSX/CSV).         |
| NFR-SEC-5 | Соблюдение правил ЭТП               | Парсер обязан уважать robots.txt и использовать официальные API, если они доступны, чтобы минимизировать риск блокировки IP.


## 4. Надежность и Наблюдаемость (Reliability & Observability)
**Заказчик**: DevOps / SRE.

| ID        | Требование                     | Метрика / Ограничение |
| :-------- | :----------------------------- | --------------------- |
| NFR-REL-1 | Доступность (Uptime)           | Доступность веб-интерфейса и API системы должна составлять не менее 99% в рабочее время (для MVP допускается 95% с автоматическим рестартом сервисов). |
| NFR-REL-2 | Обработка сбоев (Anti-Fragile) | Сбои на стороне ЭТП (ошибки 500, 503, CAPTCHA) не должны «ронять» всю систему парсинга. Ошибочные задачи должны уходить в "Dead Letter Queue (DLQ) после 3 попыток с экспоненциальным backoff (BR-06).
| NFR-OBS-1 | Трейсинг LLM (LangFuse)        | 100% запросов к LLM (включая RAG) должны логироваться в LangFuse с передачей метрик: "input_tokens", "output_tokens", "latency", "cost", "prompt_template.
| NFR-OBS-2 | Аудит действий                 | Все критичные действия пользователей (вход, смена пароля, экспорт данных, изменение профиля) должны записываться в таблицу "AUDIT_LOG с указанием timestamp и IP-адреса. Логи хранятся не менее 1 года.


## 5. Отказоустойчивость и Устойчивость к сбоям (Fault Tolerance & Resilience)
**Заказчик**: DevOps / SRE, Архитектор. Критично для сохранения данных и непрерывности работы.

| ID       | Требование                                        | Метрика / Ограничение                                                                    |
| :------- | :------------------------------------------------ | :--------------------------------------------------------------------------------------- |
| NFR-FT-1 | Сохранность задач при падении воркера             | Если воркер (scoring_service/pwin_service) падает во время обработки задачи, задача не должна быть потеряна". Очередь (Redis/RabbitMQ) должна использовать persistence, а механизм "visibility_timeout обязан возвращать задачу в очередь для повторной обработки другим инстансом.
| NFR-FT-2 | Graceful Degradation (Изоляция сбоев LLM)         | Если внешний провайдер LLM (DeepSeek/Giga) недоступен или отвечает с таймаутом > 30 сек |, система "не должна блокировать базовый парсинг". Парсинг метаданных продолжается, а глубокий анализ ТЗ переводится в статус «Отложен» с уведомлением пользователя о задержке.
| NFR-FT-3 | Circuit Breaker (Автоматическое отключение узлов) | При превышении порога ошибок (например, 5 ошибок 500 подряд от БД или конкретной ЭТП) система должна автоматически «разрывать цепь» (Circuit Breaker) и временно прекратить отправку запросов к этому узлу, чтобы предотвратить каскадный отказ (Cascading Failure).
| NFR-FT-4 | Автоматическое восстановление (Self-healing)      | В случае аварийного завершения процесса парсера, API или воркера, оркестратор (Docker Compose / systemd) должен автоматически перезапустить упавший контейнер/процесс в течение 1 минуты без ручного вмешательства.
| NFR-FT-5 | Идемпотентность обработки                         | Повторная доставка одной и той же задачи из очереди (например, из-за таймаута) не должна приводить к дублированию записей в БД или двойному списанию токенов LLM. Операции должны быть идемпотентны (проверка по "registry_number + user_id).
