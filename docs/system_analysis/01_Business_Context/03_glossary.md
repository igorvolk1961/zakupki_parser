# Глоссарий предметной области

> Термины предметной области и реализации TenderSearch. Синхронизировано с кодом и
> конфигурацией (актуализировано 2026-08-24).

| Термин | Определение |
| :----- | :---------- |
| ЕИС | Единая информационная система в сфере закупок (zakupki.gov.example). Основной источник данных по 44-ФЗ и 223-ФЗ. |
| ЭТП | Электронная торговая площадка, на которой проводятся торги (Роселторг, РАД/lot-online, Фабрикант, B2B-Center, ЭТП ГПБ, Региональный портал поставщиков). |
| 44-ФЗ / 223-ФЗ | Федеральные законы, регулирующие госзакупки в стране. 44-ФЗ — для государственных и муниципальных нужд, 223-ФЗ — для госкомпаний. |
| НМЦК | Начальная (максимальная) цена контракта. Бюджет закупки. |
| ОКПД2 / КПГЗ | Национальный классификатор продукции по видам экономической деятельности / Классификатор расходов по видам функций бюджетов. Используются для первичной классификации закупки. |
| ПП № 2571 | Постановление Правительства страны, устанавливающее требование к участникам закупок иметь подтвержденный опыт исполнения контрактов аналогичного вида. |
| Реестр Минпромторга | Государственный реестр национальной промышленной продукции. Наличие в реестре — обязательное условие для участия в ряде закупок. |
| Fit | Множитель скоринга, отражающий соответствие тендера компетенциям и ресурсам компании (0.0–1.0). |
| P(win) | Множитель скоринга — вероятность победы в тендере (формула: base × k_smp × k_license × …). |
| Margin | Множитель скоринга — маржинальность контракта (НМЦК × margin_rate). |
| Каскад скоринга | Архитектурный подход: последовательная обработка закупки стадиями Fit → P(win) → Margin. Автокаскад отключён: P(win)/Margin запускаются on-demand по запросу тендеролога. |
| Стадия каскада | Отдельный сервис-воркер очереди: `scoring_service` (Fit), `pwin_service` (P(win)), `margin_service` (Margin). |
| Воркер | Процесс, который забирает задание из очереди и обрабатывает его (stateless). |
| Очередь задач | Брокер сообщений (Redis; целевой — RabbitMQ за абстракцией `scoring_common/queue.py`). Очереди стадий: `scoring:jobs`, `pwin:jobs`, `margin:jobs`. |
| Auto-Fit | Автоматическая оценка Fit внешним LLM-скорингом для каждой сохранённой закупки (без ручной корректировки; ручная корректировка — пост-MVP). |
| Клиентская пост-фильтрация (R9) | Фильтрация закупок по позитивным словам и словам-исключениям на стороне клиента ДО записи в БД; серверная фильтрация — только по ОКПД2 (+ обход «без кода»). |
| Активный профиль | Единственный выбранный пользователем профиль фильтрации (`is_active`); его критерии и слова используются парсером и скорингом. |
| Профиль фильтрации | Настройки тендеролога: ключевые слова/исключения (таблица `keywords`), целевые ЭТП/законы, ОКПД2, диапазон НМЦК, порог Fit, компетенции, отчётные поля с условиями (`profiles.report_fields`), сайт поставщика. |
| Отчётное поле | Поле профиля (`profiles.report_fields`), значение которого программа находит в документах закупки (LLM + проверка по тексту): строка, число, дата, да/нет или список (коды, наименования, виды работ). |
| Условие поля | Оператор и значение для проверки отчётного поля: сравнение, вхождение в список, сравнение с текстом сайта; проверяет код (кроме «соответствует по смыслу» — LLM). Невыполненное условие — барьер уровня поля (отклоняет закупку / снижает P(win) / только в отчёте); непроверенное (нет данных, сайт собирается) — не барьер. |
| Сайт-источник | Сайт, текст которого собран по всем страницам пагинации и хранится в системе (`site_sources` + объектное хранилище): значение условия поля или сайт поставщика. «Полный» — пагинация закончилась сама; «неполный» — доказано только наличие значения. |
| Уточнения «рядом» | Слова, которые должны стоять рядом со значением на сайте (вид работ у кода ФККО): ищутся между значением и следующим значением той же формы; берутся из другого отчётного поля (что требует ТЗ) с метками сайта или задаются словами. |
| Требования к участнику | Требования закупки к участнику, найденные детерминированно (код, без LLM) по ВСЕМ документам: лицензии, опыт, реестр Минпромторга, соисполнители (`procurements.requirements_json`). Отметки «не установлено», «не требуется» делают требование отрицаемым (`negated`) — оно не блокирует. LLM только дозаполняет структурированные данные (`data`, платная опция). |
| Факты профиля | Названия лицензий и типы подтверждения опыта профиля; отдаются конвейеру в `GET /api/clients/active` → `facts`, используются в сводке по лицензиям (какой вид требуется и есть ли он у поставщика). Профиль в промпт LLM не попадает. |
| Анализ документов закупки | On-demand анализ: LLM извлекает значения отчётных полей профиля, код проверяет их условия, находит требования к участнику, считает расстояние до центра региона и выносит вердикт. Правка условий/блокировок пересчитывается без LLM. |
| RAG | Retrieval-Augmented Generation: чанки всех документов закупки → эмбеддинги → top-k по запросу отчётного поля (название + подсказка) → LLM извлекает значение поля. |
| Вердикт | Итог приемлемости закупки (`rag_report.verdict`) по барьерам, заданным профилем: **жёсткий** (найдено требование категории с уровнем «отклоняет», опыт через площадку ПП 2571 без такого опыта в профиле — BR-03, невыполненное условие поля уровня «отклоняет») — закупка не принята и авто-отклоняется с причиной; **мягкий** (уровень «снижает P(win)», опыт со сканами/выпиской из реестра — BR-03) — закупка принята, её P(win) снижается. Повторный анализ/пересчёт снимает своё авто-отклонение. |
| Барьер (жёсткий / мягкий) | Уровень стоп-условия профиля (`severity`): `block` — отклоняет закупку, `soft` — умножает P(win) на `soft_pwin_factor` за каждый мягкий барьер (P(win) модели сохраняется в `p_win_base`), нет уровня — только показывается в отчёте. |
| Карточка тендера | Структурированное представление закупки с базовыми полями и результатами проверок (в т.ч. `rag_report`). |
| Маркер | Представление результата в карточке: ✓/✗ — условие поля выполнено/нет, ⚪ «не проверено» (с причиной), ⏳ «сайт собирается»; блокирующее несоответствие выделено красным. |
| Service-account | Внутренний пользователь (админ) для вызовов без авторизации; до этапа 3 оценки писались под него. |
| Мультитенантность | Изоляция данных между пользователями (тенантами) по `user_id` (профили) и `profile_id` (оценки) — BR-07. |
| DLQ | Dead Letter Queue — очередь «битых» задач после N неудачных попыток для ручного разбора DevOps (этап 10). |
| Circuit breaker | Автоматическое «размыкание цепи» к узлу при превышении порога ошибок (предотвращение каскадного отказа). |
| LangFuse | Система трассировки LLM-запросов (input/output tokens, latency, cost). |
| robots.txt | Файл ограничений индексирования/парсинга на сайте; парсер обязан его уважать (US-9.2). |
| Human-in-the-loop | Паттерн, при котором пользователь участвует в валидации или дообучении алгоритма через обратную связь. |
| Тендеролог | Специалист, который ведёт сопровождение тендерной деятельности клиента. |
| Scoring Transport | Gateway каскада: принимает задания (`POST /api/scoring/jobs`), ставит их в Redis-очередь стадии, возвращает результат (`POST /score`). |
