# Глоссарий предметной области

> Термины предметной области и реализации TenderSearch. Синхронизировано с кодом и
> конфигурацией (актуализировано 2026-08-24).

| Термин | Определение |
| :----- | :---------- |
| ЕИС | Единая информационная система в сфере закупок (zakupki.gov.ru). Основной источник данных по 44-ФЗ и 223-ФЗ. |
| ЭТП | Электронная торговая площадка, на которой проводятся торги (Роселторг, РАД/lot-online, Фабрикант, B2B-Center, ЭТП ГПБ, Портал поставщиков Москвы). |
| 44-ФЗ / 223-ФЗ | Федеральные законы, регулирующие госзакупки в РФ. 44-ФЗ — для государственных и муниципальных нужд, 223-ФЗ — для госкомпаний. |
| НМЦК | Начальная (максимальная) цена контракта. Бюджет закупки. |
| ОКПД2 / КПГЗ | Общероссийский классификатор продукции по видам экономической деятельности / Классификатор расходов по видам функций бюджетов. Используются для первичной классификации закупки. |
| ПП РФ № 2571 | Постановление Правительства РФ, устанавливающее требование к участникам закупок иметь подтвержденный опыт исполнения контрактов аналогичного вида. |
| Реестр Минпромторга | Государственный реестр российской промышленной продукции. Наличие в реестре — обязательное условие для участия в ряде закупок. |
| Fit | Множитель скоринга, отражающий соответствие тендера компетенциям и ресурсам компании (0.0–1.0). |
| P(win) | Множитель скоринга — вероятность победы в тендере (формула: base × k_smp × k_license × …). |
| Margin | Множитель скоринга — маржинальность контракта (НМЦК × margin_rate). |
| Каскад скоринга | Архитектурный подход: последовательная обработка закупки стадиями Fit → P(win) → Margin. Автокаскад отключён: P(win)/Margin запускаются on-demand по запросу тендеролога. |
| Стадия каскада | Отдельный сервис-воркер очереди: `scoring_service` (Fit), `pwin_service` (P(win)), `margin_service` (Margin). |
| Воркер | Процесс, который забирает задание из очереди и обрабатывает его (stateless). |
| Очередь задач | Брокер сообщений (Redis; целевой — RabbitMQ за абстракцией `scoring_common/queue.py`). Очереди стадий: `scoring:jobs`, `pwin:jobs`, `margin:jobs`. |
| Auto-Fit | Автоматическая оценка Fit внешним LLM-скорингом для каждой сохранённой закупки (без ручной корректировки; ручная корректировка — пост-MVP). |
| Клиентская пост-фильтрация (R9) | Фильтрация закупок по позитивным словам и словам-исключениям на стороне клиента ДО записи в БД; серверная фильтрация — только по ОКПД2 (+ обход «без кода»). |
| Активный профиль | Единственный выбранный пользователем профиль фильтрации (`is_active`); его критерии и слова используются парсером и скорингом. |
| Профиль фильтрации | Настройки тендеролога: ключевые слова/исключения (таблица `keywords`), целевые ЭТП/законы, ОКПД2, диапазон НМЦК, порог Fit, компетенции, пользовательские вопросы к ТЗ (`profiles.questions`). Обязательные системные проверки в профиль не входят (см. «Системные вопросы к ТЗ»). |
| Системные вопросы к ТЗ | Фиксированный набор обязательных проверок ТЗ (опыт ПП РФ 2571, реестр Минпромторга, лицензии/СРО; ids `sys:*`, версия набора `SYSTEM_QUESTIONS_VERSION`). Хранятся вне профиля (`analysis_service`), не редактируются через профиль, применяются ко всем закупкам и пользователям. |
| Вопросы профиля (пользовательские) | Произвольные вопросы тендеролога к ТЗ из `profiles.questions` (`{id, text}`); обрабатываются per-question RAG-вызовом. Не могут дублировать системные проверки (id `sys:*` фильтруется при сохранении). |
| Факты ТЗ | Структурированное извлечение из текста ТЗ (Stage A): `required`/`confirmation` по опыту, `required`/`not_established_note` по реестру Минпромторга, `kind`/`license_code` по лицензиям. Извлекает LLM; профиль в промпт не попадает. |
| Факты профиля | Срез данных профиля для сопоставления (Stage B): коды лицензий (`license_codes`) и типов подтверждения опыта (`experience_codes`). Отдаются конвейеру в `GET /api/clients/active` → `facts`. |
| Двухстадийный анализ ТЗ | Подход: **Stage A** — извлечение фактов из ТЗ (LLM, on-demand); **Stage B** — сопоставление фактов ТЗ с фактами профиля детерминированными правилами (код, без LLM). Разделение гарантирует, что профиль не влияет на промпт. |
| RAG | Retrieval-Augmented Generation: поиск релевантных чанков ТЗ → LLM. Для системных проверок — лексический ретривал по паттернам (без эмбеддингов вопросов); для пользовательских вопросов — эмбеддинги + косинусная близость → top-k. |
| Вердикт | Результат проверки одного вопроса по фрагменту ТЗ: `absolute` (жёсткий барьер), `soft` (понижает шансы), `no_stop_condition` (нет стоп-условия). Для системных проверок вычисляется правилами Stage B; для пользовательских — LLM по тексту ТЗ. |
| Карточка тендера | Структурированное представление закупки с базовыми полями и результатами проверок (в т.ч. `rag_report`). |
| Маркер | Целевое представление результата проверки: 🔴 жёсткий барьер, 🟡 мягкое требование/уточнение, 🟢 требование не установлено/не требуется. Системные проверки в карточке помечаются `source=system`. |
| Service-account | Внутренний пользователь (админ) для вызовов без авторизации; до этапа 3 оценки писались под него. |
| Мультитенантность | Изоляция данных между пользователями (тенантами) по `user_id` (профили) и `profile_id` (оценки) — BR-07. |
| DLQ | Dead Letter Queue — очередь «битых» задач после N неудачных попыток для ручного разбора DevOps (этап 10). |
| Circuit breaker | Автоматическое «размыкание цепи» к узлу при превышении порога ошибок (предотвращение каскадного отказа). |
| LangFuse | Система трассировки LLM-запросов (input/output tokens, latency, cost). |
| robots.txt | Файл ограничений индексирования/парсинга на сайте; парсер обязан его уважать (US-9.2). |
| Human-in-the-loop | Паттерн, при котором пользователь участвует в валидации или дообучении алгоритма через обратную связь. |
| Тендеролог | Специалист, который ведёт сопровождение тендерной деятельности клиента. |
| Scoring Transport | Gateway каскада: принимает задания (`POST /api/scoring/jobs`), ставит их в Redis-очередь стадии, возвращает результат (`POST /score`). |
