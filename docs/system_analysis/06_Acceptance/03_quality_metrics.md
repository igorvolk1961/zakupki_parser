# Метрики качества данных и экономики

> Методики измерения для критериев успеха MVP (Vision & Scope K-2/K-3):
> качество отбора (ложноотрицательные/ложноположительные) и стоимость обработки.
> Связано с BR-02, NFR-COST-1/3, `TODO.md` (калибровка скоринга).

## 1. Качество отбора (SA-4.1)

### 1.1 Метрики

| Метрика | Определение | Целевой порог (согласуется на калибровке) |
| :------ | :---------- | :---------------------------------------- |
| Recall (полнота) | Доля релевантных закупок, попавших в предварительный список (не пропущенных) | ≥ 0.9 на тестовой выборке |
| Precision (точность) | Доля релевантных закупок среди показанных | ≥ 0.8 на тестовой выборке |
| Ложноотрицательные (FN) | Релевантная закупка отброшена фильтрацией/скорингом (пропуск) | минимизировать; спорные случаи маркировать, не удалять |
| Ложноположительные (FP) | Нерелевантная закупка показана (мусор) | минимизировать через слова-исключения/порог Fit |
| F1 | Гармоническое среднее Precision/Recall | ≥ 0.85 |

### 1.2 Методика оценки

1. Сформировать **тестовую выборку**: N закупок (например, 200) с целевых ЭТП за период;
   эксперт (Александр) размечает каждую закупку: «релевантна / не релевантна» + наличие
   барьеров (опыт 2571, реестр Минпромторга, лицензии).
2. Прогнать выборку через пайплайн: клиентская пост-фильтрация (R9) → Fit →
   RAG-анализ ТЗ (этап 5).
3. Сравнить результаты с разметкой эксперта: посчитать TP/FP/FN/TN, Recall, Precision, F1.
4. Спорные случаи (низкий Fit, «серые» вердикты) — анализировать отдельно: они должны
   маркироваться (🟡/«низкий приоритет»), а не отбрасываться жёстко (R-16).

### 1.3 Раздельные проверки

- **Фильтрация (R9)**: отдельно оценить, сколько релевантных закупок отброшено
  позитивными/негативными словами (ложноотрицательные фильтра) — при необходимости
  скорректировать слова профиля.
- **Скоринг Fit**: отдельно оценить распределение Fit на релевантных/нерелевантных;
  подобрать `min_fit_threshold`.
- **Анализ ТЗ (этап 5)**: точность вердиктов absolute/soft/no_stop_condition против
  разметки эксперта (в т.ч. кейс «не установлено» BR-04).

## 2. Экономическая модель (SA-4.2)

### 2.1 Метрики

| Метрика | Определение | Целевой лимит |
| :------ | :---------- | :------------ |
| Стоимость на закупку (глубокий анализ) | Затраты на LLM-токены при RAG-анализе ТЗ (промпт + вывод) | ≤ $0.05 (NFR-COST-1) |
| Стоимость на закупку (Fit) | Токены LLM-скоринга Fit (Fit → Judge → refine → ТЗ → Giga) | фиксируется для коридора |
| Стоимость повторной обработки | Обработка закупки с неизменившимися метаданными | $0 (NFR-COST-2, BR-01) |
| Средняя стоимость цикла | Итог за цикл парсинга (по площадкам) | в рамках бюджета |

### 2.2 Методика измерения

1. **Источник данных**: LangFuse-трейсы (NFR-OBS-1) — для каждого LLM-запроса
   `input_tokens`, `output_tokens`, `latency`, `cost`.
2. **Агрегация**: по `procurement_id` суммировать стоимость всех вызовов стадий
   (fit/analysis/pwin/margin) → стоимость на закупку.
3. **Лимиты промпта**: `analysis_service.settings` — `chunk_max_chars`, `top_k`;
   суммарный контекст ≤ 4000 токенов (NFR-COST-3); нерелевантные чанки отсекаются
   до отправки в модель.
4. **Контроль**: подсчёт стоимости на закупку — этап 5/10 (NFR-COST-1); при
   превышении коридора — снижение `top_k`/модели или ограничение on-demand анализа.
