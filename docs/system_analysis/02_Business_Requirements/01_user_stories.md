# Эпики и User Stories

## Эпик 1: Управление Профилем фильтрации
*Источник: Шаг 1 модели TO-BE. Роль: Тендеролог

| ID | Приоритет | User Story |
|:---|:---|:---|
| US-1.1 | **Must** | Как **Тендеролог**, я хочу задать список ключевых слов и слов-исключений для поиска, чтобы система отбирала только релевантные закупки по моей тематике. |
| US-1.2 | **Must** | Как **Тендеролог**, я хочу указать целевые ЭТП и законы (44-ФЗ, 223-ФЗ), чтобы система парсила только нужные мне площадки. |
| US-1.3 | **Should** | Как **Тендеролог**, я хочу добавить/удалить ключевое слово или исключение без участия разработчика, чтобы оперативно реагировать на изменение направления поиска. |
| US-1.4 | **Could** | Как **Тендеролог**, я хочу иметь несколько Профилей фильтрации (по разным клиентам), чтобы не перенастраивать систему каждый раз. |
| US-1.5 | **Should** | Как **Тендеролог**, я хочу задавать коды ОКПД2 как теги (добавление по Enter, удаление по «×» — как у ключевых слов) с контролем формата кода, чтобы площадки искали закупки по корректным кодам, а опечатки отсекались сразу. |
| US-1.6 | **Should** | Как **Тендеролог**, я хочу получать понятное сообщение об ошибке при попытке сохранить профиль (например, «профиль без компетенций нельзя сохранить, пока в аккаунте доступен LLM-скоринг»), чтобы понимать, что именно мешает сохранению, а не догадываться по отсутствию реакции. |

**Acceptance Criteria для US-1.1:**
- **Given**: Тендеролог открыл раздел настройки Профиля.
- **When**: Он вводит список ключевых слов (например, «искусственный интеллект», «автоматизация») и слов-исключений (например, «медицина», «ремонт»).
- **Then**: Профиль сохраняется. При следующем цикле парсинга система использует именно эти слова для первичного отбора.

**Acceptance Criteria для US-1.2:**
- **Given**: Тендеролог открыл раздел настройки Профиля.
- **When**: Он выбирает целевые ЭТП (ЕИС, Портал поставщиков Москвы, Роселторг и т.д.) и указывает законы (44-ФЗ, 223-ФЗ).
- **Then**: Профиль сохраняется. При следующем цикле парсинга система опрашивает только выбранные площадки и фильтрует закупки по указанным законам.

**Acceptance Criteria для US-1.3:**
- **Given**: Тендеролог видит в выдаче нерелевантный тендер (например, «ИИ в медицине»).
- **When**: Он добавляет слово «медицина» в список исключений.
- **Then**: При следующем цикле парсинга закупки, содержащие слово «медицина» в описании, не попадают в предварительный список.

**Acceptance Criteria для US-1.4:**
- **Given**: Тендеролог находится в разделе управления Профилями фильтрации.
- **When**: Он нажимает «Создать новый профиль», вводит название (например, «Клиент А - ИИ») и настраивает для него уникальные ключевые слова, слова-исключения и целевые ЭТП.
- **Then**: Новый профиль сохраняется в общем списке. При запуске парсинга или просмотре выдаче система позволяет выбрать активный профиль, и результаты фильтруются строго по его настройкам, не смешиваясь с другими.

**Acceptance Criteria для US-1.5:**
- **Given**: Тендеролог редактирует профиль.
- **When**: Он вводит код ОКПД2 (например, 62.02) и нажимает Enter либо удаляет код по «×».
- **Then**: Код добавляется чипом; код неверного формата (буквы, менее 2 или более 9 цифр) отклоняется с сообщением; при сохранении профиля сервер также проверяет формат кодов.

**Acceptance Criteria для US-1.6:**
- **Given**: Тендеролог нажимает «Сохранить профиль», а профиль не проходит валидацию (например, нет компетенций при доступном LLM-скоринге компетенций).
- **When**: Сервер возвращает ошибку.
- **Then**: Рядом с кнопкой сохранения и в статусной строке вкладки отображается понятный текст ошибки; редактор не закрывается, данные не теряются.

### Эпик 2: Легковесный парсинг и первичный скоринг (Fit)
*Источник: Шаги 2–3 модели TO-BE. Роль: Система.*

| ID | Приоритет | User Story |
|:---|:---|:---|
| US-2.1 | **Must** | Как **Тендеролог**, я хочу, чтобы система автоматически и периодически собирала новые закупки с целевых ЭТП, чтобы мне не нужно было вручную запрашивать выгрузки. |
| US-2.2 | **Must** | Как **Тендеролог**, я хочу, чтобы каждая закупка получала предварительную оценку соответствия (Fit) на основе названия, описания и кодов ОКПД2, чтобы я мог быстро prioritize список. |
| US-2.3 | **Must** | Как **Тендеролог**, я хочу видеть закупки отсортированными по убыванию Fit, чтобы сначала смотреть наиболее перспективные. |
| US-2.4 | **Must** | Как **Тендеролог**, я хочу, чтобы закупки, не прошедшие первичный фильтр (ключевые слова / исключения), вообще не попадали в мой список, чтобы не тратить на них внимание. |
| US-2.5 | **Should** | Как **Тендеролог**, я хочу, чтобы система не показывала повторно закупки, которые я уже отклонил, чтобы не засорять выдачу. |

**Acceptance Criteria для US-2.1:**
- **Given**: Запущен постоянный мониторинг парсера (POST `/api/parser/start`) или CLI `run-service`.
- **When**: Наступает очередной период обхода (`timeout_seconds`).
- **Then**: Система выполняет проход по целевым площадкам (ЕИС, Портал поставщиков Москвы, коммерческие ЭТП), собирает новые/обновлённые закупки и сохраняет их в БД; новые закупки автоматически ставятся в очередь внешнего скоринга Fit (ADR-7).

**Acceptance Criteria для US-2.2:**
- **Given**: Система завершила цикл парсинга и нашла 200 закупок, прошедших фильтр по ключевым словам.
- **When**: Система выполняет первичный скоринг по описанию и кодам ОКПД2.
- **Then**: Каждая закупка получает числовую оценку Fit (например, от 0 до 1). Закупки с Fit ниже минимального порога маркируются как «низкий приоритет», но **не удаляются** из базы.

**Acceptance Criteria для US-2.3:**
- **Given**: В предварительном списке есть 20 закупок с разными оценками Fit (от 0.3 до 0.95).
- **When**: Тендеролог открывает список.
- **Then**: Закупки отсортированы по убыванию Fit: сначала закупки с Fit=0.95, затем 0.90 и т.д. Закупки с Fit ниже порога (например, 0.3) помечены как «низкий приоритет», но не скрыты.

**Acceptance Criteria для US-2.4:**
- **Given**: В Профиле задано слово-исключение «медицина».
- **When**: Система обрабатывает закупку с названием «Внедрение ИИ в медицинскую информационную систему».
- **Then**: Закупка отбрасывается клиентской пост-фильтрацией ДО записи в БД (R9, `parser/filtering.py`) и не попадает в предварительный список Тендеролога.

**Acceptance Criteria для US-2.5:**
- **Given**: Тендеролог ранее отклонил закупку с реестровым номером 0173200001426000139.
- **When:** Система выполняет новый цикл парсинга и находит ту же закупку (или ее обновление).
- **Then**: Закупка не отображается в предварительном списке, но доступна в архиве/истории отклоненных закупок.

### Эпик 3: Доставка предварительного списка Тендерологу
*Источник: Шаг 4 модели TO-BE. Роль: Система → Тендеролог.*

| ID | Приоритет | User Story |
|:---|:---|:---|
| US-3.1 | **Must** | Как **Тендеролог**, я хочу получать оповещение в **Telegram** о появлении **высокорелевантных** закупок (с Fit ≥ заданного порога), чтобы не пропустить срочные дедлайны. |
| US-3.2 | **Must** | Как **Тендеролог**, я хочу видеть в предварительном списке базовые поля карточки (реестровый номер, заказчик, закон, НМЦК, дедлайн подачи, предмет закупки, Fit), чтобы принять решение о дальнейшей обработке без открытия внешних сайтов. |
| US-3.3 | **Should** | Как **Тендеролог**, я хочу иметь возможность экспортировать предварительный список в XLSX/CSV, чтобы передать его клиенту или работать офлайн. |

> **US-3.4 удалён** (решение заказчика): дайджест с топ-3 закупок не нужен. Оповещается
> только о появлении высокорелевантных закупок — по каждой закупке отдельно (US-3.1).

> **Операционное ограничение доставки (Telegram ↔ ЭТП):** Telegram требует VPN для доступа
> из РФ, а ЭТП (в т.ч. ЕИС) **не работают при включённом VPN**. Парсинг выполняется без
> VPN, поэтому отправка оповещения в Telegram возможна только в моменты, когда VPN доступен
> (например, вручную/отдельным процессом). Доставка — best-effort: недоступность канала в
> момент отправки не влияет на парсинг и не роняет систему.

> **Текущее состояние (Эпик 3):** уведомления реализованы **постадийно** — после каждой
> стадии каскада (fit/pwin/margin) при прохождении её порога (`notify_min_fit_score` /
> `notify_min_pwin` / `notify_min_margin`), каналы Telegram/MAX/Webhook (`config_ops.yaml`).
> Экспорт в MVP — **CSV**; целевой XLSX (US-3.3) — этап 8 (пост-MVP).

**Acceptance Criteria для US-3.1:**
- **Given**: Система завершила цикл парсинга и нашла закупку с Fit ≥ порога релевантности (например, 0.7).
- **When**: Выполнена оценка Fit закупки.
- **Then**: Тендеролог получает оповещение в **Telegram** по каждой такой закупке с полями карточки: реестровый номер, заказчик, закон, НМЦК, дедлайн подачи, предмет закупки, Fit, ссылка на ЭТП. Уведомление формируется по факту появления закупки (не сводкой/дайджестом).

**Acceptance Criteria для US-3.2:**
- **Given**: В предварительном списке есть 15 закупок, отсортированных по Fit.
- **When**: Тендеролог открывает список.
- **Then**: Для каждой закупки отображаются: реестровый номер, наименование заказчика, закон (44/223), НМЦК, дедлайн подачи заявки, краткий предмет закупки, оценка Fit. Для перехода к полному тексту на ЭТП доступна внешняя ссылка.

**Acceptance Criteria для US-3.3:**
- **Given**: В предварительном списке есть 15 закупок.
- **When**: Тендеролог нажимает «Экспорт в XLSX».
- **Then**: Файл XLSX скачивается. Файл содержит колонки: реестровый номер, заказчик, закон, НМЦК, дедлайн подачи, предмет закупки, Fit, ссылка на ЭТП. Форматирование сохранено (числа, даты, гиперссылки).

### Эпик 4: Инициация и выполнение детальной проверки ТЗ
*Источник: Шаги 5–6 модели TO-BE v2.0. Роль: Тендеролог → Система.*

> **Текущее состояние (Эпик 4):** RAG-анализ ТЗ реализован **двухстадийно**
> (`analysis_service/pipeline/rag.py` + `matcher.py`): **Stage A** — извлечение фактов
> из ТЗ. Обязательные системные проверки (опыт ПП РФ 2571, реестр Минпромторга,
> лицензии/СРО; ids `sys:*`) — один batch-LLM-вызов по лексически отобранным секциям;
> пользовательские вопросы профиля — per-question вызовы (эмбеддинги → top-k).
> **Stage B** — сопоставление фактов ТЗ с фактами профиля (лицензии, подтверждённый
> опыт, BR-03) детерминированными правилами → вердикт `absolute`/`soft`/
> `no_stop_condition` + маркер 🔴/🟡/🟢. Результат — `rag_report` в карточке; профиль
> в промпт не попадает. Системные проверки вынесены за пределы профиля
> (`profiles.questions` фильтрует `sys:*`, см. BR-03/BR-04, FR-4.3).

| ID | Приоритет | User Story |
|:---|:---|:---|
| US-4.1 | **Must** | Как **Тендеролог**, я хочу для выбранной закупки инициировать детальную проверку ТЗ на наличие специфических барьеров, чтобы не тратить ресурсы системы на все подряд. |
| US-4.2 | **Must** | Как **Тендеролог**, я хочу, чтобы система проверила ТЗ на требование подтвержденного опыта исполнения контрактов (в т.ч. по ПП РФ № 2571) и указала тип требования: «жесткий допуск через площадку» или «мягкое подтверждение сканами актов». |
| US-4.3 | **Must** | Как **Тендеролог**, я хочу, чтобы система проверила ТЗ на наличие требования к реестру Минпромторга и корректно интерпретировала пометку «не установлено», даже если выше расположен длинный юридический текст. |
| US-4.4 | **Must** | Как **Тендеролог**, я хочу, чтобы система проверила ТЗ на наличие требований к лицензиям и указала, какая именно лицензия требуется. |
| US-4.5 | **Should** | Как **Тендеролог**, я хочу, чтобы результаты проверки отображались в Карточке тендера в виде понятных статусных маркеров (например: «🔴 Жесткий барьер: опыт через площадку», «🟡 Мягкое требование: сканы актов», «🟢 Реестр Минпромторга: не установлено»). |


**Acceptance Criteria для US-4.1:**
- **Given**: Тендеролог просматривает Карточку закупки в предварительном списке.
- **When**: Он нажимает кнопку «Проанализировать ТЗ».
- **Then**: Система инициирует процесс загрузки и анализа документации с ЭТП. В интерфейсе отображается статус: «Идет анализ ТЗ...». После завершения статус меняется на «Анализ завершен», и Карточка обновляется маркерами.

**Acceptance Criteria для US-4.2:**
- **Given**: Тендеролог нажал «Проанализировать ТЗ» для конкретной закупки.
- **When**: Система обрабатывает текст ТЗ.
- **Then**: В Карточке появляется маркер. Если в ТЗ найдена формулировка, соответствующая ПП РФ № 2571 (подтверждение опыта через площадку), маркер: «🔴 Требуется подтвержденный опыт исполнения контрактов на площадке». Если требование опыта допускает предоставление сканов актов — маркер: «🟡 Опыт: допускается подтверждение сканами договоров/актов».

**Acceptance Criteria для US-4.3:**
- **Given**: В ТЗ закупки присутствует абзац о запрете иностранной продукции со ссылкой на нормативный акт, а ниже через два пробела и тире написано курсивом «не установлено».
- **When**: Система выполняет проверку на требование реестра Минпромторга.
- **Then**: Маркер в Карточке: «🟢 Реестр Минпромторга: требование не установлено». Закупка **не** помечается как заблокированная.

**Acceptance Criteria для US-4.4:**
- **Given**: Тендеролог инициировал анализ ТЗ для закупки, где требуется лицензия МЧС на деятельность по монтажу пожарной сигнализации.
- **When**: Система обрабатывает текст ТЗ.
- **Then**: В Карточке появляется маркер: «🔴 Требуется лицензия: МЧС (монтаж пожарной сигнализации)». Если лицензия не требуется — маркер: «🟢 Лицензии: не требуется».

**Acceptance Criteria для US-4.5:**
- **Given**: Система завершила анализ ТЗ для закупки.
- **When**: Тендеролог открывает Карточку.
- **Then**: В разделе «Специфические проверки» отображаются маркеры:
        Опыт: 🔴 / 🟡 / 🟢
        Реестр Минпромторга: 🔴 / 🟡 / 🟢
        Лицензии: 🔴 / 🟢
        (Другие проверки, если добавлены)
    Цветовая кодировка: 🔴 — жесткий барьер, 🟡 — мягкое требование / уточнение, 🟢 — требование не установлено / не требуется.

### Эпик 5: Финальное решение и обратная связь
*Источник: Шаги 7–8 модели TO-BE. Роль: Тендеролог.*

> **Текущее состояние (Эпик 5):** решения по карточке реализованы. «Отклонить»
> (US-5.1/5.2) — статус ``rejected`` + причина в ``procurement_evaluations``
> (per-profile, колонки зарезервированы под Эпик 5), отклонённые скрываются из
> выдачи (показ отклонённых — фильтр). «В работу» (US-5.4–5.6) — отдельная
> таблица ``procurement_work_items`` на уровне профиля (``profile_id``, BR-07)
> со снимком карточки; вкладка «В работе»; приём из результатов поиска и по URL;
> снятие с работы удаляет только запись. US-5.3 (предложение добавить слово/
> правило в профиль без автоприменения и без повторов) — **отложен** (пост-MVP).

| ID | Приоритет | User Story |
|:---|:---|:---|
| US-5.1 | **Must** | Как **Тендеролог**, я хочу принять решение по проверенной Карточке: «В работу» или «Отклонить», чтобы система учитывала мой выбор. |
| US-5.2 | **Should** | Как **Тендеролог**, при отклонении я хочу указать причину (например, «не наш профиль», «слишком низкая НМЦК», «нет нужной лицензии»), чтобы система могла предложить обновление Профиля. |
| US-5.3 | **Could** | Как **Тендеролог**, я хочу, чтобы система на основе моих отклонений предлагала новые слова-исключения или правила для добавления в Профиль, чтобы сокращать долю мусора в будущих выдачах. *(Отложено: механика «предложения» реализуется пост-MVP.)* |
| US-5.4 | **Must** | Как **Тендеролог**, я хочу принять закупку «в работу» прямо из результатов поиска, чтобы вести её в отдельном списке своих активных закупок. |
| US-5.5 | **Should** | Как **Тендеролог**, я хочу добавить закупку «в работу» по URL на ЭТП (не дожидаясь её появления в результатах поиска), чтобы фиксировать интересные мне закупки сразу. |
| US-5.6 | **Must** | Как **Тендеролог**, я хочу видеть раздел «В работе» и убирать из него закупки (без удаления самой закупки из общей выдачи), чтобы управлять своим рабочим списком. |


**Acceptance Criteria для US-5.1:**
- **Given**: Тендеролог просматривает Карточку закупки с результатами анализа ТЗ.
- **When**: Он нажимает «В работу» или «Отклонить».
- **Then**:
        Если «В работу»: закупка помечается как «В работе», доступна в разделе «Активные закупки».
        Если «Отклонить»: закупка помечается как «Отклонена», не отображается в будущих выдачах (если не включена опция показа отклоненных).


**Acceptance Criteria для US-5.2:**
- **Given**: Тендеролог просматривает Карточку с маркером «🟡 Опыт: допускается подтверждение сканами».
- **When**: Он нажимает «Отклонить» и выбирает причину «Нет релевантного опыта для предоставления сканов».
- **Then**: Закупка помечается как отклоненная с указанной причиной. Закупка не показывается повторно в будущих выдачах.

**Acceptance Criteria для US-5.3:**
- **Given**: Тендеролог отклонил закупку и указал причину (например, выбрал из списка «Не наш профиль: медицина» или ввел текст «нет лицензии МЧС»).
- **When**: Система обрабатывает решение об отклонении.
- **Then**: Немедленно (в том же интерфейсе, сразу после подтверждения отклонения) система отображает предложение:
        Если причина содержит слово или фразу, которой еще нет в списке исключений текущего Профиля: «Добавить "медицина" в список слов-исключений профиля [Название профиля]?» с кнопками «Добавить» / «Не добавлять».
        Если причина указывает на тип барьера (например, «нет нужной лицензии»), система может предложить: «Добавить правило "требуется лицензия МЧС" в список обязательных проверок профиля?»
    Дополнительные условия:
        Система не применяет изменения автоматически — только предлагает. Тендеролог подтверждает или отклоняет предложение.
        Если Тендеролог уже несколько раз отклонял похожие закупки по одной и той же причине, но отклонял предложения системы, система не повторяет одно и то же предложение (чтобы не раздражать пользователя).
        Предложение отображается один раз на каждое уникальное отклонение. Если Тендеролог нажал «Не добавлять», система запоминает это и не предлагает снова для аналогичной формулировки.
    *Примечание: механика «предложения» (первое и второе условия) отложена — см. статус US-5.3; сейчас при отклонении доступны явные действия «убрать ключевые слова из профиля» и «добавить слово-исключение».*

**Acceptance Criteria для US-5.4:**
- **Given**: Тендеролог просматривает карточку закупки из результатов поиска.
- **When**: Он нажимает «В работу».
- **Then**: Закупка появляется во вкладке «В работе» активного профиля, в таблице поиска у неё отображается признак «в работе»; карточка остаётся доступной для анализа как обычно.

**Acceptance Criteria для US-5.5:**
- **Given**: Тендеролог открыл вкладку «В работе».
- **When**: Он вставляет URL закупки на ЭТП и нажимает «Принять в работу по URL».
- **Then**: Если закупка с таким URL уже есть в базе — она привязывается к записи «в работе»; если нет — создаётся запись «в работе» со снимком URL, которая не пропадает при последующей очистке результатов поиска.

**Acceptance Criteria для US-5.6:**
- **Given**: В разделе «В работе» есть закупки активного профиля.
- **When**: Тендеролог удаляет одну из них из «в работе».
- **Then**: Удаляется только запись «в работе»; сама закупка остаётся в общей выдаче результатов поиска.

## Эпик 7: Управление доступом и мультитенантность (Must для бизнес-проекта)

| ID     | Приоритет | User Story                           |
| :----- | :-------- | :----------------------------------- |
| US-7.1 | Must      | Как Тендеролог (новый пользователь), я хочу самостоятельно зарегистрироваться на сайте сервиса, указав email и контактные данные, чтобы получить trial-доступ и оценить продукт без ожидания одобрения администратора |
| US-7.2 | Must      | Как Тендеролог, я хочу получить trial-доступ на определенный период (по умолчанию — 14 дней; детали — Эпик 10) после регистрации, чтобы оценить функционал системы (оплата подписки не обязательна) |
| US-7.3 | Must      | Как Тендеролог, я хочу, чтобы по окончании trial-периода мой аккаунт был заморожен (данные сохранены, доступ к функционалу прекращен), если я не оплатил подписку, чтобы не потерять накопленные настройки и историю |
| US-7.4 | Must      | Как Тендеролог, я хочу получать неоднократные предупреждения о приближении конца trial-периода и о предстоящей заморозке через указанные при регистрации каналы связи (email, Telegram, Max), чтобы успеть принять решение об оплате |
| US-7.5 | Should    | Как Тендеролог, я хочу, чтобы после определенного периода неактивности замороженного аккаунта (например, 90 дней) система уничтожила мои данные с предварительным уведомлением, чтобы не хранить устаревшую информацию |
| US-7.6 | Must      | Как Системный администратор, я хочу контролировать общее число зарегистрированных аккаунтов (активных, замороженных, неактивных), видеть статистику и при необходимости решать проблемы пользователей, связанные с их аккаунтами |
| US-7.7 | Must      | Как Системный администратор, я хочу создавать учетные записи других администраторов, чтобы распределить нагрузку по поддержке пользователей |
| US-7.8 | Must      | Как Тендеролог, я хочу, чтобы мои Профили фильтрации, Карточки тендеров и история действий были изолированы от других пользователей, чтобы гарантировать конфиденциальность данных моих клиентов |
| US-7.9 | Must      | Как Архитектор/DevOps, я хочу, чтобы база данных была спроектирована с поддержкой мультитенантности (через "user_id"), чтобы обеспечить изоляцию данных на уровне БД |

> **Решение MVP (Эпик 7):** trial-период по умолчанию — **14 дней** (`TRIAL_DEFAULT_DAYS`),
> оплата/подписка **не обязательны** (можно не оплачивать; платёжный шлюз и `subscriptions` —
> вне MVP). По истечении trial пользователь **не замораживается**, а переводится на набор
> бесплатных опций своего аккаунта (см. Эпик 10); заморозка и удаление данных (BR-05) —
> целевая модель, пост-MVP. Подтверждение email при регистрации — целевая модель, в MVP
> **не реализуется** (заглушка: ссылка логируется).

> **Текущее состояние (Эпик 7):** регистрация/логин реализованы (`users.username/email/
> password_hash/roles`, PBKDF2). Реализованы аккаунты пользователя с платными опциями
> (`user_accounts`, активен один), триал-режим (`users.trial_end_at`, по умолчанию 14 дней),
> личный кабинет (аккаунты/опции, смена пароля), админ-управление аккаунтами и триалом
> (см. Эпик 10). Подтверждение email, `subscriptions`, заморозка/удаление аккаунтов
> (BR-05) и `audit_log` — целевая модель, пост-MVP.

**Acceptance Criteria для US-7.1:**
- **Given**: Пользователь перешел на страницу регистрации сервиса.
- **When**: Он заполняет форму (email, пароль, имя, телефон/Telegram для уведомлений); подтверждение email через ссылку — в MVP не требуется (см. «Решение MVP»).
- **Then**: Учетная запись создается, пользователь автоматически получает роль «Тендеролог» и trial-доступ с датой окончания (по умолчанию — через 14 дней; см. Эпик 10). Администратор не участвует в этом процессе.

**Acceptance Criteria для US-7.2:**
- **Given**: Тендеролог зарегистрировался и получил trial-доступ (по умолчанию — 14 дней).
- **When**: В течение trial-периода Тендеролог выполняет любые действия (создает Профили, парсит тендеры, экспортирует данные).
- **Then**: Все реализованные опции поиска и скоринга доступны бесплатно. После окончания trial-периода платные опции определяются активным аккаунтом пользователя (по умолчанию — только бесплатные, см. Эпик 10); заморозка аккаунта (BR-05) — целевая модель, пост-MVP.

**Acceptance Criteria для US-7.3:**
- **Given**: Trial-период Тендеролога истек, оплата не произведена.
- **When**: Наступает дата окончания trial.
- **Then**: Аккаунт переходит в статус «Заморожен». При входе пользователь видит сообщение: «Ваш trial-период завершен. Для восстановления доступа оплатите подписку. Все ваши данные сохранены в течение 90 дней». Профили, история и карточки остаются в базе, но недоступны для редактирования или использования.

> **MVP-поведение:** заморозка (BR-05) — целевая модель пост-MVP. В текущей реализации по
> истечении trial-периода пользователь переводится на бесплатные опции активного аккаунта
> (см. Эпик 10): доступ не блокируется, платные операции просто недоступны.

**Acceptance Criteria для US-7.4:**
- **Given**: У Тендеролога активен trial-период, указаны контактные данные (email, Telegram).
- **When**: До конца trial остается 7 дней, 3 дня и 1 день.
- **Then**: Система отправляет уведомления на все указанные каналы связи с текстом: «До окончания вашего trial-периода осталось N дней. Оплатите подписку, чтобы сохранить доступ к данным и настройкам» со ссылкой на страницу оплаты.

**Acceptance Criteria для US-7.5:**
- **Given**: Аккаунт Тендеролога находится в статусе «Заморожен» уже 90 дней.
- **When**: Наступает 90-й день заморозки.
- **Then**: За 7 дней до уничтожения система отправляет финальное уведомление: «Ваш аккаунт будет удален через 7 дней из-за неактивности. Все данные будут безвозвратно удалены». По истечении 90 дней все данные аккаунта (Профили, Карточки, история) физически удаляются из базы данных.

**Acceptance Criteria для US-7.6:**
- **Given**: Администратор авторизован в системе.
- **When**: Он открывает раздел «Управление пользователями».
- **Then**: Отображается список всех аккаунтов с фильтрами по статусу (Активен / Trial / Заморожен / Удален). Для каждого аккаунта видны: email, дата регистрации, дата последней активности, статус. Администратор может вручную продлить trial, разморозить аккаунт или удалить его.

**Acceptance Criteria для US-7.7:**
- **Given**: Администратор с правом управления ролями авторизован.
- **When**: Он создает новую учетную запись и назначает роль «Администратор».
- **Then**: Новый пользователь получает полные права администратора. Создание обычных пользователей через эту форму невозможно (они регистрируются самостоятельно).

**Acceptance Criteria для US-7.8:**
- **Given**: В системе зарегистрированы Тендеролог А и Тендеролог Б.
- **When**: Тендеролог А выполняет запрос к API на получение списка своих Профилей или Карточек.
    Then: Система возвращает только записи, где tenant_id соответствует Тендерологу А. Попытка запросить данные Тендеролога Б возвращает HTTP 403 Forbidden.

**Acceptance Criteria для US-7.9:**
- **Given**: В системе настроена схема БД с полем tenant_id во всех пользовательских таблицах.
- **When**: Любая операция чтения/записи выполняется приложением.
- **Then**: На уровне ORM (Object-Relational Mapping) автоматически добавляется фильтр WHERE tenant_id = :current_tenant_id, предотвращающий утечку данных между пользователями даже при ошибке в коде.

# Эпик 9: Юридическая безопасность и Compliance
*Контекст: Система работает с парсингом внешних данных и автоматической интерпретацией юридических документов (ТЗ). Это создает риски: нарушение правил использования ЭТП, некорректная трактовка требований, претензии со стороны пользователей.*

> **Текущее состояние (Эпик 9):** дисклеймер в UI/экспортах (US-9.1), robots.txt
> (US-9.2), маскирование ПДн (US-9.3), полный audit_log (US-9.4) — этапы 6/9/10
> (пост-MVP). Секреты в env (NFR-SEC-2) и tenant-изоляция (BR-07) реализованы.

| ID     | Приоритет | User Story                   |
| :----- | :-------- | :--------------------------- |
| US-9.1 | Must      | Как Юрист компании, я хочу, чтобы во всех интерфейсах и экспортируемых отчетах присутствовал дисклеймер об информационной природе скоринга, чтобы минимизировать юридические риски компании |
| US-9.2 | Must      | Как Юрист компании, я хочу, чтобы система при парсинге ЭТП учитывала файл "robots.txt" и использовала официальные API там, где это требуется, чтобы избежать претензий за нарушение правил использования площадок |
| US-9.3 | Should    | Как Юрист компании, я хочу, чтобы система автоматически маскировала или не сохраняла персональные данные физических лиц (если они встречаются в текстах закупок), чтобы соблюдать 152-ФЗ «О персональных данных» |
| US-9.4 | Should    | Как Системный администратор, я хочу, чтобы система логировала все действия пользователей (создание профилей, отклонение тендеров, экспорт данных) с указанием времени и IP-адреса, чтобы обеспечить возможность аудита в случае спорных ситуаций |

**Acceptance Criteria для US-9.1:**
- **Given: Тендеролог просматривает Карточку тендера с результатами скоринга или формирует отчет в XLSX.
- **When: Страница загружается или файл генерируется.
- **Then: Внизу карточки или на отдельном листе/в подвале файла XLSX виден текст: «Результаты автоматизированного скоринга носят исключительно информационный характер и не являются юридической консультацией. Окончательное решение о соответствии требованиям закупки и подаче заявки принимает пользователь».

**Acceptance Criteria для US-9.2:**
- **Given: Система начинает парсинг новой ЭТП.
- **When: Модуль парсинга инициализируется.
VThen: Система сначала запрашивает и анализирует файл robots.txt целевого домена. Если robots.txt запрещает парсинг определенных путей, система не обращается к ним. Если для ЭТП существует официальный API, система использует его вместо прямого парсинга HTML.

**Acceptance Criteria для US-9.3:**
- **Given: В тексте ТЗ встречается персональное данные физического лица (например, ФИО контактного лица, телефон).
- **When: Система сохраняет данные закупки в базу.
- **Then: Персональные данные либо не сохраняются (удаляются на этапе парсинга), либо маскируются (например, телефон сохраняется как +7***123). В экспортируемых отчетах персональные данные отсутствуют.

**Acceptance Criteria для US-9.4:**
- **Given: Тендеролог выполняет действие (создает Профиль, отклоняет тендер, экспортирует данные).
- **When: Действие завершается.
- **Then: В системный лог (или таблицу audit_log) записывается: timestamp, user_id, action_type, resource_id, ip_address. Логи хранятся не менее 1 года и доступны для просмотра Администратором.

## Эпик 10: Аккаунты пользователя и платные опции (монетизация операций)

> **Контекст:** операции, которые стоят владельцу системы (вызовы LLM/эмбеддингов, платные
> гео-сервисы), лицензируются через «аккаунт пользователя» — именованный набор
> переключателей платных опций. У пользователя может быть несколько аккаунтов, активен
> один; активный аккаунт определяет доступность платных операций после окончания
> триал-режима. Бесплатные опции доступны всегда. Каталог опций живёт в коде
> (`zakupki_parser/options.py`); в БД хранятся только переключатели (`user_accounts.options`).

| ID | Приоритет | User Story |
|:---|:---|:---|
| US-10.1 | **Must** | Как **Тендеролог**, я хочу заходить в «Личный кабинет» по кнопке в основном интерфейсе и видеть: статус триала, свои аккаунты и каталог операций (бесплатные и платные), чтобы понимать, какой функционал мне доступен. |
| US-10.2 | **Must** | Как **Тендеролог**, я хочу для каждой платной операции (скоринг по компетенциям, эмбеддинги при анализе, анализ LLM, P(win), Margin; в перспективе — платное геопозиционирование) выбирать, доступна она мне или нет, чтобы управлять платными операциями и их стоимостью. |
| US-10.3 | **Must** | Как **Тендеролог**, я хочу создавать несколько именованных аккаунтов (наборов опций), переключать активный аккаунт и удалять неактивные, чтобы иметь разные профили использования (например, «полный» и «экономный»). |
| US-10.4 | **Must** | Как **Тендеролог**, я хочу менять свой пароль в личном кабинете (с проверкой текущего пароля), чтобы поддерживать безопасность учётной записи. |
| US-10.5 | **Must** | Как **Тендеролог**, я хочу, чтобы по умолчанию мой аккаунт включал только бесплатные опции (поиск/сбор, «В работе», уведомления, экспорт), а платные я включал сам, чтобы не платить за то, что не использую. |
| US-10.6 | **Must** | Как **Тендеролог**, я хочу после самостоятельной регистрации получить триал-режим на 14 дней (по умолчанию), в котором все опции поиска и скоринга доступны бесплатно, чтобы оценить продукт целиком. |
| US-10.7 | **Must** | Как **Тендеролог**, я хочу, чтобы профиль можно было сохранить без компетенций, если мой аккаунт не предусматривает обработку компетенций языковой моделью (опция «Скоринг по компетенциям» выключена), чтобы использовать профиль как поисковый (ключевые слова/ОКПД2/НМЦК). |
| US-10.8 | **Must** | Как **Системный администратор**, я хочу просматривать и редактировать аккаунты и опции любого пользователя, а также выдавать/продлевать/снимать триал, чтобы управлять доступом пользователей к платным операциям. |
| US-10.9 | **Should** | Как **Тендеролог**, я хочу, чтобы система не выполняла платные операции, недоступные в моём текущем триале/аккаунте (включая фоновый сбор и до-постановку очереди скоринга), и объясняла причину отказа, чтобы у меня не возникало неожиданных расходов. |

**Acceptance Criteria для US-10.1:**
- **Given**: Тендеролог вошёл в систему.
- **When**: Он нажимает «Кабинет» (или вкладку «Личный кабинет»).
- **Then**: Отображаются статус триала (дата окончания, остаток дней), список аккаунтов с признаком активного и каталог опций: бесплатные — «всегда доступны», платные — с состоянием «включена/выключена в аккаунте» и пометкой «активна сейчас» (триал).

**Acceptance Criteria для US-10.2:**
- **Given**: Тендеролог открыл раздел «Опции активного аккаунта».
- **When**: Он включает/выключает платные опции и нажимает «Сохранить опции».
- **Then**: Изменения сохраняются в активном аккаунте. Недоступные для подключения опции (например, платное геопозиционирование до подключения сервиса) показаны как «недоступно» и не переключаются.

**Acceptance Criteria для US-10.3:**
- **Given**: У Тендеролога есть аккаунты.
- **When**: Он создаёт новый аккаунт, переключает активность или удаляет неактивный.
- **Then**: Активен всегда ровно один аккаунт; удалить последний или активный аккаунт нельзя (сначала активировать другой). Переключение активного аккаунта сразу меняет фактически доступные платные операции.

**Acceptance Criteria для US-10.4:**
- **Given**: Тендеролог в разделе «Смена пароля».
- **When**: Он вводит текущий и новый пароль (дважды) и сохраняет.
- **Then**: При корректном текущем пароле пароль обновляется; при неверном — сообщение «Неверный текущий пароль» без раскрытия причины.

**Acceptance Criteria для US-10.5:**
- **Given**: Пользователь создал аккаунт или у него закончился триал.
- **When**: Он открывает каталог опций.
- **Then**: Все бесплатные опции доступны; платные — выключены (доступны после включения пользователем/администратором). В личном кабинете бесплатные опции видны с пометкой «бесплатно, всегда доступно».

**Acceptance Criteria для US-10.6:**
- **Given**: Пользователь самостоятельно зарегистрировался.
- **When**: Регистрация завершена.
- **Then**: У пользователя выставлен trial_end_at = now()+14 суток; в триале все реализованные платные опции поиска и скоринга доступны бесплатно (в UI — плашка «триал N дн.» и баннер в кабинете). По умолчанию создан аккаунт «По умолчанию» только с бесплатными опциями — он начнёт действовать после окончания триала.

**Acceptance Criteria для US-10.7:**
- **Given**: Тендеролог сохраняет профиль, в котором нет компетенций.
- **When**: Активный аккаунт не включает опцию «Скоринг по компетенциям (LLM)».
- **Then**: Профиль сохраняется (например, профиль только с кодами ОКПД2). Если опция включена — сохранение отклоняется с сообщением: «Профиль без компетенций нельзя сохранить: LLM-скоринг по компетенциям доступен в вашем аккаунте. Отключите опцию в личном кабинете, чтобы сохранять профили без компетенций».

**Acceptance Criteria для US-10.8:**
- **Given**: Администратор открыл пользователя во вкладке «Пользователи».
- **When**: Он нажимает «Опции».
- **Then**: Отображаются аккаунты пользователя, активный из них и каталог опций; администратор может создавать/переименовывать/удалять аккаунты, переключать активный, менять платные опции и управлять триалом (установить на N дней / снять).

**Acceptance Criteria для US-10.9:**
- **Given**: У пользователя закончился триал и в активном аккаунте выключены платные опции.
- **When**: Пользователь пытается запустить анализ документов или P(win)/Margin, либо у него остались неоценённые закупки в очереди скоринга.
- **Then**: On-demand операции отклоняются с сообщением о необходимости включить опции; фоновый сбор и recovery-постановка очереди не ставят задачи скоринга для такого владельца.
