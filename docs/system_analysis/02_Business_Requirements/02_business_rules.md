# Бизнес-правила (BR)

| BR-01 | Частота парсинга и кэширование (Экономия) | Система не должна тратить ресурсы на повторную обработку неизменившихся данных.<br><br>«ЕСЛИ» закупка уже есть в базе («number + platform_id») «И» её дата обновления на ЭТП не изменилась,<br>«ТО» пропустить парсинг (дедуп; ранний пропуск по `known_numbers`).<br>«ЕСЛИ» число результатов поиска площадки ≤ числа записей БД по площадке (`total_results` early-exit),<br>«ТО» завершить проход досрочно (реализовано, этап 3).<br>«ЕСЛИ» дата обновления изменилась,<br>«ТО» запустить лёгкий парсинг (обновление метаданных).<br>«ЕСЛИ» статус закупки на ЭТП стал «Работа завершена» / «Контракт заключен»,<br>«ТО» пометить закупку как неактивную (архив) и исключить из активных выдач.<br>«ЕСЛИ» включён кэш ответов ЭТП (R4, этап 4A),<br>«ТО» повторная обработка неизменившихся страниц не выполняется (стоимость ≈ $0). | Дмитрий (требование экономии) | US-2.1, NFR-COST-2, NFR-PERF-2, ER: PROCUREMENT; этапы 3, 4 (4A) |
| BR-02 | Первичный скоринг (Fit) и клиентская пост-фильтрация | Оценка соответствия (от 0.0 до 1.0) и отбор закупок.<br><br>«ЕСЛИ» закупка не содержит ни одного позитивного слова профиля ИЛИ содержит слово-исключение,<br>«ТО» закупка отбрасывается **клиентской пост-фильтрацией ДО записи в БД** (R9, `parser/filtering.py`) и не сохраняется.<br>«ЕСЛИ» закупка прошла фильтр «И» совпадает по кодам ОКПД2 (серверный запрос площадки),<br>«ТО» закупка сохраняется в БД и для неё ставится задание внешнего скоринга Fit (auto-Fit, LLM-пайплайн `scoring_service`); оценка пишется в `procurement_evaluations` под активный профиль (BR-07).<br>«ЕСЛИ» Fit < минимального порога (`min_fit_threshold` профиля, например 0.3),<br>«ТО» закупка сохраняется в БД, но не попадает в предварительный список «релевантных» и не порождает оповещения (порог применяется при выдаче/уведомлении). | Александр (методология отбора) | US-2.2, US-2.3, US-2.4, US-3.1, NFR-PERF-1, ER: KEYWORD, PROCUREMENT_EVALUATION; этап 3 (R9), калибровка — пост-MVP |
| BR-03 | Валидация требования опыта (ПП РФ № 2571) | Критическое правило для допуска к тендеру.<br><br>«ЕСЛИ» в ТЗ найдена ссылка на ПП РФ № 2571 ИЛИ фраза «опыт должен быть подтвержден на электронной площадке»,<br>«ТО» маркер: 🔴 Жёсткий барьер (требуется профиль на площадке).<br>«ЕСЛИ» в ТЗ требуется опыт, но допускается предоставление «сканов договоров/актов» или «выписок из реестра контрактов»,<br>«ТО» маркер: 🟡 Мягкое требование.<br>«ЕСЛИ» опыт упоминается только в критериях оценки (как дополнительные баллы),<br>«ТО» маркер: 🟢 Не является барьером допуска.<br><i>Текущее состояние: реализовано системной проверкой `sys:exp_2571` (Stage A — извлечение фактов из ТЗ; Stage B — правила в `analysis_service/pipeline/matcher.py`): `platform` без подтверждённого опыта в профиле → 🔴, `documents`/`registry` → 🟡, `evaluation_only` → 🟢. Маркер в карточке `source=system`.</i> | Александр (SME) | US-4.2, US-4.5, NFR-COST-1/3, ER: PROCUREMENT_EVALUATION; этап 5 |
| BR-04 | Контекстный анализ реестра Минпромторга | Защита от ложных срабатываний на юридические преамбулы.<br><br>«ЕСЛИ» в разделе «Требования к продукции» найден текст о запрете иностранной продукции<br>«НО» в конце раздела/абзаца есть пометка «не установлено» (или аналогичная по смыслу),<br>«ТО» маркер: 🟢 Требование не установлено.<br>«ЕСЛИ» пометки «не установлено» нет,<br>«ТО» маркер: 🔴 Требуется выписка из реестра Минпромторга.<br><i>Текущее состояние: реализовано системной проверкой `sys:minprom_registry` (Stage A извлекает факт «не установлено»; BR-04): требование установлено → 🔴, пометка «не установлено» → 🟢.</i> | Александр (SME) | US-4.3, US-4.5, NFR-COST-1/3, ER: PROCUREMENT_EVALUATION; этап 5 |
| BR-05 | Жизненный цикл аккаунта (Trial/Freeze — целевая модель) | Управление доступом в SaaS-модели.<br><br>(Реализовано) «ЕСЛИ» пользователь зарегистрировался самостоятельно,<br>«ТО» trial_end_at = now()+14 дней (TRIAL_DEFAULT_DAYS); в триале все реализованные опции поиска и скоринга бесплатны.<br>«ЕСЛИ» trial закончился,<br>«ТО» платные операции определяются активным аккаунтом пользователя (по умолчанию — только бесплатные опции, BR-09; доступ НЕ блокируется).<br>(Целевое, пост-MVP) «ЕСЛИ» текущая дата > дата_окончания_trial «И» оплата не поступила,<br>«ТО» статус аккаунта = «Заморожен», доступ к функционалу закрыт (BR-05 целевая).<br>«ЕСЛИ» статус «Заморожен» длится > 90 дней,<br>«ТО» инициировать процедуру физического удаления данных (с уведомлением за 7 дней).<br><i>Текущее состояние: trial_end_at (14 дней по умолчанию) и аккаунты опций (user_accounts) реализованы; заморозка/удаление, уведомления 7/3/1 и `subscriptions` — целевая модель пост-MVP.</i> | Бизнес-модель (Дмитрий) | US-7.1–7.5, US-10.6, BR-09, ER: USER (trial_end_at), USER_ACCOUNT; этап 6 |
| BR-06 | Обработка ошибок парсинга (Anti-Fragile) | Защита системы от сбоев внешних ЭТП.<br><br>«ЕСЛИ» парсер получил ошибку 429 (Too Many Requests) или CAPTCHA,<br>«ТО» приостановить парсинг этого домена на N минут (экспоненциальный backoff).<br>«ЕСЛИ» после 3 попыток задача не выполнилась (ошибка 500, битый PDF, недоступность ЭТП),<br>«ТО» задача перемещается в Dead Letter Queue (DLQ) для ручного разбора DevOps, чтобы не блокировать очередь.<br><i>Текущее состояние: retry/backoff/recovery, circuit breaker реализованы; явной DLQ нет — этап 10.</i> | Игорь / DevOps | US-8.3, NFR-REL-2, NFR-FT-1/3/4, ER: PROCUREMENT; этапы 4, 10 |
| BR-07 | Изоляция данных (Multi-tenancy) | Абсолютное правило безопасности.<br><br>ВСЕГДА при любом запросе на чтение/запись данных Тендера, Профиля или Карточки<br>ДОБАВЛЯТЬ условие WHERE user_id = :current_user_id (оценки и решения «в работе» — по `profile_id`).<br>Обход этого правила на уровне приложения запрещён.<br><i>Реализовано (этап 1): tenant-скоуп репозитория по `user_id`, оценки — по `profile_id`, внутренние вызовы — только X-Internal-Token. Решения «В работе» (`procurement_work_items`) изолированы по `profile_id` (этап 7, US-5.4–5.6).</i> | Юрист / Архитектор | US-7.8, US-7.9, US-5.4–5.6, NFR-SEC-1, ER: USER, PROFILE, PROCUREMENT_EVALUATION, PROCUREMENT_WORK_ITEM, SUBSCRIPTION, AUDIT_LOG; этап 1 (реализовано) |
| BR-08 | Сохранность решений «в работе» | Решения тендеролога не должны пропадать при очистке результатов поиска.<br><br>«ЕСЛИ» закупка принята «в работу» «И» её запись удаляется из общей базы (очистка БД devops),<br>«ТО» запись «в работе» сохраняется: `procurement_id` обнуляется (FK `ON DELETE SET NULL`), карточка отдаётся из снимка ключевых полей в самой записи.<br>«ЕСЛИ» devops явно запросил удаление «в работе» (`include_work_items=true`),<br>«ТО» записи «в работе» удаляются вместе с закупками.<br><i>Реализовано (этап 7): `procurement_work_items` — снимок + `ON DELETE SET NULL`, чекбокс в модалке очистки БД.</i> | Дмитрий / Игорь | US-5.4–5.6, NFR-SEC-1, ER: PROCUREMENT_WORK_ITEM; этап 7 |
| BR-09 | Аккаунты пользователя и платные опции | Доступность платных операций (LLM/эмбеддинги/внешние сервисы) определяется «аккаунтом» пользователя.<br><br>ВСЕГДА активен ровно один аккаунт пользователя (набор переключателей платных опций `user_accounts.options`); пользователь сам переключает активный аккаунт в личном кабинете, администратор — во вкладке «Пользователи».<br>«ЕСЛИ» действует триал (trial_end_at > now),<br>«ТО» все реализованные опции поиска и скоринга доступны бесплатно независимо от аккаунта.<br>«ЕСЛИ» триал не действует,<br>«ТО» платные опции доступны только если включены в активном аккаунте; по умолчанию аккаунт включает только бесплатные опции.<br>«ЕСЛИ» платная операция (скоринг по компетенциям, эмбеддинги при анализе, анализ LLM, P(win), Margin; платное гео — отложено) недоступна,<br>«ТО» операция не выполняется (on-demand — понятный отказ; фоновый сбор и recovery-очередь не ставят задачи для такого владельца).<br>«ЕСЛИ» активный аккаунт не включает обработку компетенций языковой моделью (опция «Скоринг по компетенциям»),<br>«ТО» профиль можно сохранить и без компетенций (поисковый профиль: слова/ОКПД2/НМЦК). | Дмитрий / Бизнес-модель | US-10.1–10.9, BR-05, ER: USER, USER_ACCOUNT, USER (trial_end_at); этап 6 |
