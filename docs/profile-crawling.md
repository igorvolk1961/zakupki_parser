# Мультипрофильный обход площадок и дедупликация запросов

Парсер обходит площадки сразу для нескольких профилей фильтрации (по профилю на
пользователя, BR-07). Каждый профиль задаёт **критерии поиска** (коды ОКПД2, диапазон
НМЦК, активность) и **слова/вопросы** (ключевые слова, слова-исключения, вопросы к ТЗ).
Слова и вопросы применяются **клиентски** после получения списка закупок (R9) — серверный
запрос к площадке они не меняют.

## Поисковые обходы (CrawlUnit)

Для площадки `orchestrator._build_units` строит список поисковых обходов:

- **по кодам ОКПД2** (`kind=codes`) — если у профиля есть коды и площадка фильтрует по ним;
- **обход «без кода»** (`kind=no_code`, R9) — отдельный проход по всему реестру площадки,
  если включён `search_criteria.no_code_search` и у профиля есть позитивные слова.

Ключ дедупликации — `_criteria_units_key` (`kind` + отсортированные коды ОКПД2 +
`nmck_min` + `nmck_max` + `active_only`). Совпадающий ключ ⇔ идентичный запрос к площадке.

## Параметр `deduplicate_requests`

- **`true` (по умолчанию)** — профили с совпадающим ключом объединяются в **один**
  `CrawlUnit`: запрос к площадке выполняется один раз, полученный список веерно
  фильтруется под каждый профиль.
- **`false`** — каждый профиль получает **собственный** обход (отдельный запрос к площадке),
  даже если его критерии совпадают с другими профилями.

## Когда отключать (`false`)

1. **Нужна независимая статистика/логи обхода по каждому профилю.** При дедупликации
   обход и сводка (`_log_crawl_summary`) — общие на группу профилей, без привязки
   результата к конкретному профилю-инициатору. Отдельные проходы дают собственную
   статистику и трейсы на профиль.
2. **Изоляция запроса по профилю.** Если планируется, что запрос к площадке будет
   зависеть от индивидуальных настроек профиля (свои query-параметры, пагинация,
   стейт, ретраи по-профильно) — объединение таких запросов сломает изоляцию.
3. **Диагностика и отладка площадки.** Отдельный запрос проще сопоставить с конкретным
   профилем и набором критериев — удобно локализовать сбой, лимит, пустой ответ или
   антибот-капчу конкретного профиля.
4. **Пиковые объёмы.** Один общий запрос может вернуть большой список, который затем
   фильтруется в памяти одного юнита под множество профилей. Раздельные проходы дают
   меньшие порции (ценой N-кратного роста числа запросов).

## Когда отключать НЕ нужно

- Обычная работа с несколькими профилями: дедупликация снижает нагрузку на площадку
  и вероятность `rate limit`/блокировок, ускоряет проход.
- Различия профилей **только** по ключевым словам/исключениям/вопросам — они
  клиентские и дедупликации не мешают.
- **Один профиль** — параметр не влияет (совпадающих обходов нет).

## Взаимодействие с параллельной обработкой площадок

Обход всегда идёт в порядке `platform_then_profile` (снаружи площадки, внутри
профили) — опция обратного порядка (`profile_then_platform`) удалена. Включённые
площадки обрабатываются параллельными `asyncio`-задачами с лимитом
`config_parser.yaml -> max_concurrent_platforms` (R5): задержка/backoff одной
площадки не блокирует другие. Одинаковые обходы (одинаковые коды ОКПД2/НМЦК)
разных профилей к одной площадке объединяются в один `CrawlUnit` (дедупликация),
поэтому запрос к площадке выполняется один раз, а список веерно фильтруется под
каждый профиль.

Если нужна изоляция или независимая статистика обхода строго по профилю — это
достигается отключением дедупликации (`deduplicate_requests: false`), при котором
`_build_units` создаёт отдельный `CrawlUnit` на профиль (отдельный обход и отдельная
сводка), а не переключением порядка циклов.
