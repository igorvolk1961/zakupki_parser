# Контракт взаимодействия с внешними сервисами

Документ описывает взаимодействие парсера закупок с внешними сервисами:
**обработки файлов** и **скоринга**. Парсер отдаёт данные и принимает результаты
через REST API.

---

## 1. Роли

| Сторона | Что делает |
|---|---|
| **Парсер** (`zakupki-parser`) | Собирает закупки, хранит метаданные в PostgreSQL (колонки + `files_json`, `detail_json`), предоставляет REST API |
| **Внешний сервис обработки файлов** | Скачивает файлы закупки (по URL из `files_json`), распаковывает архивы (ZIP и др.), находит техническое задание, возвращает его метаданные |
| **Внешний сервис скоринга** | По характеристикам закупки считает score и возвращает результат |

---

## 2. Что парсер предоставляет внешнему сервису

### 2.1 Данные закупки
- `GET /api/procurements` — список с фильтрами (`number`, `platform_id`, `okpd2`,
  `customer`) и пагинацией (`limit`, `offset`);
- `GET /api/procurements/{id}` — карточка закупки, включая `detail_json`
  (полный снимок переменных) и `files_json`.

### 2.2 Метаданные файлов (`files_json`)
Парсер **не скачивает** файлы: для каждого файла закупки сохраняется пара
`{name, url}` (URL скачивания с ЭТП). Техническое задание хранится в `files_json`
наравне с остальными файлами (никаких отдельных полей).

> **Важно:** если ТЗ лежит **внутри ZIP-архива** (имя архива не совпадает с
> ключевыми словами ТЗ), парсер его по имени не определяет — распаковку и поиск
> ТЗ выполняет внешний сервис обработки файлов (см. п. 3.2).

---

## 3. Обработка файлов (внешний сервис)

### 3.1 Обычные файлы
Внешний сервис скачивает файлы по `url` из `files_json`, извлекает из них
переменные (PDF/DOCX) по своей внутренней логике.

### 3.2 ТЗ внутри ZIP
1. Парсер сохраняет ZIP-архив в `files_json` (имя+URL).
2. Внешний сервис скачивает архив, распаковывает, находит внутри файл, чьё имя
   совпадает с ключевыми словами ТЗ (по конфигурации парсера или своей).
3. Внешний сервис обрабатывает найденный ТЗ.

---

## 3. Скоринг (внешний сервис)

### 3.0 Каскад скоринга Fit → P(win) → Margin

Внешний скоринг — каскад из независимых стадий, соединённых очередями Redis:

1. **Fit** (`scoring_service`) — LLM-пайплайн, возвращает `fit_score` (0..1) и
   `score_method=fit`.
2. **P(win)** (`pwin_service`) — считает    `P(win) = base_pwin × k_smp × k_license ×
   k_large × k_procedure` и возвращает `p_win` (`score_method=pwin`).
3. **Margin** (`margin_service`) — считает маржу (`НМЦК × margin_rate`) и возвращает
   `margin` (`score_method=margin`).

Множители хранятся в БД **per-profile** (`procurement_evaluations`) **отдельными
полями** (`fit_score`, `p_win`, `margin`); `score` — накопленное произведение
(после завершённой стадии = `fit × p_win × margin`).

**Оркестрация — парсером**: обработчик `POST /api/procurements/{id}/score` пишет
результат стадии профилю из `body.profile_id` (BR-07). **Автокаскад отключён**:
после сохранения закупки ставится только авто-Fit; P(win)/Margin вычисляются по
явному запросу тендеролога (`POST /api/procurements/pwin-margin` — обе стадии сразу,
флаги `pwin_enabled`/`margin_enabled`). Пороги переходов `pwin_fit_threshold`/
`margin_pwin_threshold` удалены (ADR-10).

### 3.1 Постановка задачи на скоринг (конвейер, ADR-7)

Внешний скоринг выполняется асинхронным конвейером `scoring_transport` + сервисы
стадий + Redis:
1. Парсер после сохранения новой закупки передаёт задание в **транспорт**:
   `POST /api/scoring/jobs {procurement_id, priority, stage="fit", profile_id}`.
   Приоритет — время обновления/публикации закупки; `profile_id` — профиль, по
   компетенциям которого считается скор (пер-профильно, BR-07).
2. Транспорт маршрутизирует задание по `stage` в Redis-очередь соответствующей стадии
   (`scoring:jobs`/`pwin:jobs`/`margin:jobs`/`analysis:jobs`); сервис стадии
   обрабатывает его и публикует результат; транспорт возвращает его в парсер через
   `POST /score` (см. п. 3.2).

> Прежние способы прямого вызова внешнего сервиса парсером (`external_call_mode:
> before_save` — `POST external_service_url` перед записью; `external_call_mode: worker` —
> воркер по записям со `score_method=default`) удалены (ADR-7) — внешний скоринг идёт
> только через конвейер транспорт + сервис скоринга.

### 3.2 Возврат score (через транспорт)
```
POST /api/procurements/{id}/score
Content-Type: application/json
X-Internal-Token: <ZAKUPKI_INTERNAL_TOKEN>

{
  "score": 0.35,
  "score_method": "fit",
  "fit_score": 0.7,
  "p_win": 0.5,
  "margin": 200.0,
  "profile_id": 1,
  "embedding_similarity": 0.81,
  "rag_report": { ... }
}
```
Ответ: `200` с обновлённой карточкой. `404` — закупка не найдена.

Эндпоинт защищён внутренним токеном `X-Internal-Token` (env `ZAKUPKI_INTERNAL_TOKEN`).
`profile_id` — профиль, которому пишется результат (пер-профильно, BR-07);
`rag_report` сохраняется отдельно и не меняет `score_method`.

Значения `score_method`: `default` | `fit` | `pwin` | `margin` | `deadline_expired` | `sim`
(`deadline_expired` выставляется парсером при просроченном сроке подачи, `score=0`).
`fit`/`pwin`/`margin` — стадии внешнего каскада скоринга; авто-переход между стадиями
отключён — P(win)/Margin запускаются только по запросу тендеролога. `sim` —
предварительная фильтрация сервиса скоринга по векторной близости (близость ниже
порога `embedding_filter_threshold`): LLM не выполнялся, `score=0` и `fit_score=0`.
Порог задаётся аналитиком в `config_service.yaml -> scoring` (вкладка «Параметры
мониторинга`) и применяется воркером через `GET /api/config/scoring`.

## 5. Фоновая индексация закупок+документов по ОКПД2 (`indexing_service`)

Отдельная стадия конвейера — **вне каскада Fit → P(win) → Margin** (нет `score`/
`profile_id`: индекс общий на закупку, не per-profile). Цель — устранить
необходимость живого повторного обхода площадок при смене профиля фильтрации
для закупок из конфигурируемого диапазона ОКПД2 (`IndexingConfig`,
`config_service.yaml -> indexing`): «горячий» пересбор отвечает мгновенно из
Postgres full-text search (`procurement_search_index`) вместо обхода ЭТП.

### 5.1 Кто ставит задание

Системный «индексный» профиль (`zakupki_parser.scheduler._build_system_index_ctx`,
не привязан к пользователю, не хранится в БД) участвует в обычном обходе
площадок наравне с пользовательскими профилями — по семантике «пустой список
ключевых слов, фильтра нет» сохраняются **все** закупки указанного диапазона
ОКПД2, независимо от чьих-либо ключевых слов. Для каждой такой закупки парсер
(`RecordProcessingMixin._enqueue_index_job`, `parser/orchestrator/processing.py`)
дозагружает `files_json` (тем же общим интерфейсом `extract_details`, что и
`POST /score`, п. 3.1) и ставит задание:

```
POST /api/scoring/jobs {"procurement_id": ..., "priority": ..., "stage": "index", "profile_id": 0}
```

`indexing_service` **не водит браузер** (архитектурная граница: Playwright — только
внутри парсера) — файлы уже дозагружены парсером на этом шаге.

### 5.2 Обработка (indexing_service)

Воркер получает задание из Redis-очереди `index:jobs` (транспорт маршрутизирует
по `stage="index"`, как и остальные стадии, п. 3.1), читает карточку закупки
(`GET /api/procurements/{id}`, `files_json` уже заполнен), скачивает и извлекает
текст документов (`scoring_common.tz`, тот же модуль, что у `analysis_service`),
публикует результат в `index:results`.

### 5.3 Возврат результата

```
POST /api/procurements/{id}/index-result
Content-Type: application/json
X-Internal-Token: <ZAKUPKI_INTERNAL_TOKEN>

{
  "status": "indexed",
  "document_text": "текст технического задания и приложений",
  "content_hash": "sha256-хэш текста (идемпотентное переиндексирование)"
}
```

`status`: `indexed` (текст извлечён, возможно частично — по успешным файлам) |
`error` (не удалось обработать ни одного файла — `error_message`, повтор на
следующей итерации фонового обхода). Парсер сам вычисляет `okpd2_normalized` из
актуального `procurements.okpd2_codes` (не принимается от сервиса) и делает upsert
в `procurement_search_index` (`ProcurementRepository.save_index_result`). Повторный
`error`-результат **не затирает** `document_text`/`content_hash` предыдущего
успешного результата — обновляются только явно переданные поля.

`search_tsv` — генерируемая Postgres-колонка (`GENERATED ALWAYS AS ... STORED`,
конфигурация `to_tsvector('simple', ...)`, НЕ `'russian'` — см. докстринг
`storage/db/search_index.py`): матчинг ключевых слов профиля транслируется в
tsquery тем же способом, что и клиентский DSL-движок (`parser/filtering.py`) —
см. `parser/filtering_tsquery.py`.

### 5.4 Живой фоллбэк вне индекса (`Profile.search_in_documents`)

Профильная опция «искать ключевые слова в документах» работает **везде**, не
только в проиндексированном диапазоне: для закупок вне `IndexingConfig.
okpd2_prefixes` парсер сам (в живом обходе, `RecordProcessingMixin.
_live_fallback_document_text`) дозагружает детали+файлы и скачивает документы —
без участия `indexing_service`. Это заметно медленнее (осознанный компромисс,
нет предвычисленного индекса вне заданного диапазона) — единственный способ
ускорить эту часть в будущем — расширять `okpd2_prefixes`.

### 5.5 Бэкофилл

При первом включении/расширении `okpd2_prefixes` историю закупок этого
диапазона, отфильтрованных ДО включения индексации (когда-то не совпавших ни с
чьими ключевыми словами и потому не сохранённых), индексный профиль сам не
увидит — нужен один разовый проход с расширенным окном обхода
(`default_cutoff_days`) по площадкам для этого диапазона ОКПД2, чтобы подтянуть
историю; затем `indexing_service` догонит бэклог документов обычным темпом.

## 4. Ограничения и согласования
- **ZIP-кейс**: парсер не определяет ТЗ внутри архива — это ответственность внешнего
  сервиса (ADR-5).
- **Авторизация** служебных вызовов конвейера — внутренний токен
  `X-Internal-Token` (env `ZAKUPKI_INTERNAL_TOKEN`); транспорт передаёт его через
  `TRANSPORT_PARSER_INTERNAL_TOKEN`.
- **Анализ ТЗ** (`analysis_service`) — доставка результата проходит тем же конвейером:
  парсер ставит задание `stage="analysis"` (через `POST /api/procurements/analyze`),
  сервис возвращает `rag_report` через `POST /score` (см. п. 3.2).
- **Индексация** (`indexing_service`) — отдельная стадия вне каскада, см. раздел 5.
- Форматы payload и порядок согласуются при интеграции парсера в общую архитектуру
  (ADR-3, ADR-5).
