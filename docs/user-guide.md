# Руководство пользователя

Система «Парсер закупок» собирает сведения о государственных и муниципальных
закупках с площадок (zakupki.mos.ru, ЕИС и др.), сохраняет их в базе данных
PostgreSQL и предоставляет веб-интерфейс для просмотра и управления.

Система **не зависит от источника данных**: парсер работает с реальными
площадками, при этом интерфейс одинаково отображает закупки из любого наполнения БД.

---

## 1. Запуск

### 1.1. Быстрый старт

1. Поднимите фоновый стек (БД + Redis + воркеры каскада скоринга/анализа +
   `scoring_transport`) — см. «Запуск» в `README.md` (например, `./scripts/run_all.sh`).
2. Запустите сервис:

   ```bash
   uv run zp --configs configs serve
   ```

   При старте автоматически применяются миграции БД (Liquibase), если это необходимо.

3. Откройте в браузере адрес: **http://localhost:8000/**

Миграции применяются автоматически для команд, работающих с БД: `serve`,
`run-once`, `run-service`, `seed-profile`.

---

## 2. Вход и роли

Приложение открывается сразу на главной странице — обязательного входа нет.
В самом верху расположено меню: **Документация**, **Техподдержка**, **Контакты**,
**Вход**. Пункт **Вход** открывает модальное окно **Вход / Зарегистрироваться**
(после входа на его месте появляются имя пользователя и кнопка **Выйти**):

- **Вход** — логин и пароль (Bearer-токен создаётся на сервере).
- **Зарегистрироваться** — самостоятельная регистрация: логин, пароль и его
  подтверждение, email. Роль при регистрации — **простой пользователь** (`user`).

До входа доступны только справочные разделы (руководство и меню); вкладки
рабочего пространства и данные закупок появляются после входа.

Роли (может быть несколько у одного пользователя): `user` — базовый доступ
(закупки, заказчики, профили); `admin` — управление пользователями; `analyst` —
аналитические настройки (параметры мониторинга, промпты, справочники); `devops` —
эксплуатация (конфиги ops/log/parser, логи, управление парсером и БД).
Роли `admin`/`analyst`/`devops` назначает администратор во вкладке **Пользователи**.

Набор вкладок главной страницы — **объединение** вкладок всех ролей пользователя.
Заблокированный аккаунт (`blocked`) не может войти.

## 3. Веб-интерфейс

Верхнее меню: **Документация**, **Техподдержка**, **Контакты** и блок пользователя
(до входа — **Вход**; после — имя, роли и кнопка **Выйти**). Шапка: название
системы и версия, состояние парсера, переключатель **активного профиля**
(клиент) и выбор цветовой схемы.

### 3.1. Панель «Парсер»

Кнопки управления сбором:

- **▶ Запустить** — запускает постоянный мониторинг парсера (периодические проходы).
  Во время работы кнопка становится недоступной.
- **■ Остановить** — останавливает текущий проход (браузер корректно закрывается).
- **Очистить БД** — диалог очистки БД (всё / только неактивные / нерелевантные с
  порогом fit-score). Доступна только при остановленном парсере; требует подтверждения.

Рядом выводится статус: «не запущен», «работает…», либо сообщение об ошибке и
время завершения.

### 3.2. Вкладки

База (`user`/`analyst`):

- **Закупки** — список собранных закупок.
- **Заказчики** — справочник заказчиков (наименование, ИНН, рейтинг).
- **Профили** — профили фильтрации пользователя.

По ролям (`admin`/`analyst`/`devops`):

- **Пользователи** (admin) — управление пользователями.
- **Параметры мониторинга** (analyst) — форма по схеме `config_service.yaml`.
- **Промпты** (analyst) — редактор промптов сервисов.
- **Справочники** (analyst) — справочные таблицы (типы лицензий, типы подтверждения опыта).
- **Сервисы** (devops) — конфиги фоновых сервисов + секреты `.env`.
- **Конфигурация** (devops) — `config_ops.yaml`.
- **Управление логами** (devops) — `config_log.yaml`.
- **Логи** (devops) — просмотр хвоста файла лога.
- **Парсер** (devops) — форма по схеме `config_parser.yaml` (параметры браузера/антиблок-мер) + «Текстовый режим» с сырым YAML.

### 3.3. Закупки

Слева — таблица: **ID**, предмет закупки, площадка, fit-score, статус, дата
публикации. Фильтры: сортировка (по релевантности / по дате публикации), площадка,
активность, чекбокс **«Только релевантные»** с настраиваемым порогом fit-score.

- **Клик по строке** — выбрать закупку; **Ctrl + клик** — добавить/убрать из выделения.
- Выбранные закупки отображаются карточками справа; клик по карточке — полная
  информация (заказчик, НМЦК, сроки, ОКПД2, файлы, текст ТЗ, требования к участнику,
  анализ документов, ссылка на оригинал, трейс LangFuse).
- Пакетные действия: **Анализировать документы** (авто-Fit + анализ требований к
  участнику и вопросов профиля), **Оценить P(win)/Margin** (on-demand),
  **Выгрузить CSV**.

Обновления происходят **автоматически** по WebSocket-каналу: при появлении новой
закупки или изменении данных список обновляется без перезагрузки страницы.

### 3.4. Заказчики

Таблица: **ID**, наименование, ИНН, рейтинг. Рейтинг заполняется внешним сервисом
(ADR-4/ADR-6); если ещё не рассчитан — отображается «–».

### 3.5. Профили

Профиль фильтрации — контекст обработки закупок пользователя (BR-07): ключевые
слова, слова-исключения, компетенции (текст для LLM-скоринга), критерии поиска
(коды ОКПД2, диапазон НМЦК), вопросы к ТЗ, целевые ЭТП/законы, порог Fit.
Редактор имеет под-вкладки: **Ключевые слова**, **Лицензии** (тип, номер, орган,
срок), **Опыт** (подтверждённый опыт и тип подтверждения). Профиль может быть
включён/выключен; **активный профиль — единственный** (по нему работают парсер и
скоринг). Доступны экспорт профиля в JSON, импорт и засид из файла-сида.

### 3.6. Пользователи (admin)

Создание пользователей (роли `admin`/`analyst`/`devops`; роль `user` — только
саморегистрация), смена ролей (кроме простых и себя), блокировка/разблокировка и
удаление (нельзя — себя и последнего `admin`).

### 3.7. Параметры мониторинга (analyst)

Форма по схеме аналитических параметров `config_service.yaml` (площадки и их
активность, интервал дат, правила поиска, правила оценки скоринга, дедупликация
обходов). **«Текстовый режим»** — сырой YAML. Секреты токенов в YAML не пишутся —
они берутся из env. Изменения применяются **при следующем запуске парсера**.

### 3.8. Промпты (analyst)

Редактор файлов промптов сервисов (`scoring_service` и `analysis_service`): просмотр
и сохранение Markdown/JSON-файлов; JSON-промпты проверяются на корректность до записи.

### 3.9. Справочники (analyst)

Редактор справочных таблиц: **типы лицензий**, **типы подтверждения опыта**.
Коды предустановленных записей (сид BR-03) защищены от переименования.

### 3.10. Сервисы (devops)

Под-вкладки на каждый фоновый сервис (**Скоринг**, **Анализ документов**, **P(win)**,
**Margin**): форма по схеме `src/<service>/config.yaml` (сгруппирована по смыслу) +
**«Текстовый режим»** с сырым YAML. Секреты сервиса редактируются в модальном окне
**«Секреты (.env)»** (формы `KEY=VALUE`) и в `config.yaml`/форму не попадают.
Кнопка **«⟳ Перезагрузить»** (у сервисов **Скоринг** и **Анализ документов**) перезапускает
соответствующий фоновый сервис (останавливает работающий воркер и поднимает его
заново той же командой, что и `scripts/run_all.sh`).

### 3.11. Конфигурация / Управление логами (devops)

Форма для `config_ops.yaml` и `config_log.yaml` (+ «Текстовый режим» с сырым YAML).
Секреты (auth.secret, токены уведомлений) через API не редактируются — они берутся
из env. Изменения применяются при следующем старте сервиса. Флаг
`auto_start_monitoring` управляет автозапуском цикла мониторинга при старте сервиса
(по умолчанию включён); при выключенном флаге мониторинг запускается только кнопкой
на панели devops.

### 3.12. Логи (devops)

Просмотр хвоста файла лога: поиск, фильтр по уровню («ошибки/предупреждения») и по
дате, автообновление. Управление сбором логов всех сервисов — единое в `data/logs/`
(см. `README.md`).

### 3.13. Парсер (devops)

Форма по схеме `config_parser.yaml` (параметры браузера/антиблок-мер: задержки, UA,
stealth, лимиты) + **«Текстовый режим»** с сырым YAML и кнопкой **«Сохранить»**.
Изменения применяются при следующем старте сервиса. Кнопка **«⟳ Перезагрузить»**
перезапускает парсер (останавливает текущий проход и запускает постоянный
мониторинг заново).

---

## 4. Команды командной строки

Все команды запускаются через `uv run zp --configs configs …` (короткое имя `zp`;
длинное `zakupki-parser` доступно как алиас).

| Команда | Назначение |
|---|---|
| `zp check-config` | Проверка конфигурации и вывод её параметров (без обращения к БД) |
| `zp run-once` | Один проход по всем включённым площадкам |
| `zp run-service` | Периодический запуск по таймеру (`timeout_seconds` из `config_ops.yaml`) |
| `zp stop [--force]` | Остановка запущенных процессов парсера (мягко, затем принудительно) |
| `zp serve [--host H] [--port P]` | Запуск веб-интерфейса и REST API |
| `zp capture-fixture [--platform id] [--out DIR]` | Сохранение HTML-фикстур страниц для разработки/тестов |
| `zp seed-profile [--user USER] [--file FILE]` | Заполнение профиля пользователя словами/компетенциями из файла-сида |

---

## 5. Уведомления

Парсер может уведомлять о новых закупках через **Telegram**, **MAX** или
**webhook** — настраивается в `config_ops.yaml → notifications`
(`backend: telegram | max | webhook`). Уведомление отправляется для новых закупок
после расчёта скоринга — **после каждой стадии каскада** (fit/pwin/margin), если
результат стадии изменён и прошёл её порог (`notify_min_fit_score`/`notify_min_pwin`/
`notify_min_margin` в `config_ops.yaml`). Подробнее: `docs/telegram-subscriber.md`,
`docs/max-subscriber.md`.

## 6. Частые вопросы

**После запуска парсера список не обновился.**
Запуск сбора выполняется в том же процессе, что и веб-интерфейс; обновление — по
WebSocket автоматически. Если сервис запущен со старой версией кода — перезапустите
`uv run zp serve` и обновите страницу.

**Поле ИНН у заказчика пустое.**
ИНН извлекается со страницы организации (mos.ru, ЕИС, ЭТП). Если страница изменилась
и извлечение не сработало, ИНН остаётся пустым (nullable) — закупка при этом
сохраняется.

**Где хранятся данные?**
В PostgreSQL: таблица закупок `procurements`, справочники `customers`, `platforms`,
`procedure_types`, `procedure_type_mappings` и мультитенантные таблицы `profiles`,
`keywords`, `procurement_evaluations` (BR-07), а также справочники BR-03
(`license_types`, `experience_confirmation_types`, `profile_licenses`,
`profile_experience`). Схема поддерживается миграциями Liquibase, которые
применяются автоматически при старте.

**Что делать при сбое сбора на одной площадке?**
Сбой одной площадки не останавливает остальные; он учитывается в circuit-breaker'е
для вежливой деградации и логируется. Ошибки доступны в файле лога
(`data/logs/parser.log`) и во вкладке «Логи» (devops).
