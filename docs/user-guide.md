# Руководство пользователя

Система «Парсер закупок» собирает сведения о государственных и муниципальных
закупках с площадок (zakupki.mos.ru, ЕИС и др.), сохраняет их в базе данных
PostgreSQL и предоставляет удобный веб-интерфейс для просмотра и управления.

Система **не зависит от источника данных**: парсер работает с реальными
площадками, при этом интерфейс одинаково отображает закупки из любого
наполнения БД.

---

## 1. Запуск

### 1.1. Быстрый старт

1. Убедитесь, что запущена база данных PostgreSQL (см. раздел «Запуск» в `README.md`).
2. Запустите сервис:

   ```bash
   uv run zp --configs configs serve
   ```

   При старте автоматически применяются миграции БД (Liquibase), если это
   необходимо.

3. Откройте в браузере адрес: **http://localhost:8000/**

Миграции применяются автоматически для команд, работающих с БД: `serve`,
`run-once`, `run-service`.

---

## 2. Веб-интерфейс

Верхняя строка содержит название системы, чекбокс **«Режим администратора»**
(справа) и статистику: количество закупок и заказчиков.

### 2.1. Панель «Парсер»

Кнопки управления сбором:

- **▶ Запустить** — запускает один проход парсера по всем включённым площадкам.
  Во время работы кнопка становится недоступной.
- **■ Остановить** — останавливает текущий сбор (браузер корректно закрывается).
  Доступна только во время сбора.
- **Очистить БД** — диалог удаления данных из БД (всё / только неактивные /
  нерелевантные с порогом fit-score). **Доступна только в режиме администратора
  и при остановленном сборе**. Требует подтверждения.
- **Выгрузить CSV** — выгрузка активных и релевантных закупок из БД в CSV-файл на
  сервере (каталог `export_dir` из `config_ops.yaml`, по умолчанию
  `data/export/procurements.csv`, кодировка UTF-8 с BOM — открывается в Excel).
  Также только в режиме администратора.
- Выпадающий список **«Все площадки»** — фильтр по источнику (площадке).

Рядом выводится статус: «не запущен», «остановлен», «работает…», либо сообщение
об ошибке и времени завершения сбора.

### 2.2. Вкладки

- **Закупки** — список собранных закупок.
- **Заказчики** — справочник заказчиков (наименование, ИНН, рейтинг).
- **Параметры** — просмотр и редактирование параметров сервиса
  (`config_service.yaml`). **Доступна только в режиме администратора.**

### 2.3. Просмотр закупок

Слева — таблица с двумя колонками: **ID** записи в базе и **описание** закупки
(номер и предмет). Справа — область детального просмотра выбранных закупок.

- **Клик по строке** — выбрать закупку (одну).
- **Ctrl + клик** — добавить закупку к выделению или убрать её из выделения.
- Выбранные закупки отображаются карточками справа.
- Клик по карточке — открыть полную информацию о закупке (заказчик, НМЦК, сроки,
  ОКПД2, файлы, ссылка на оригинал и т.д.).

Обновления происходят **автоматически**: при появлении новой закупки или изменении
данных список обновляется по WebSocket-каналу без перезагрузки страницы и кнопки
«Обновить».

### 2.4. Заказчики

Таблица с заказчиками: ID, наименование, ИНН, рейтинг. Рейтинг заполняется
внешним сервисом (ADR-4); если рейтинг ещё не рассчитан, отображается «–».

### 2.5. Режим администратора

Чекбокс **«Режим администратора»** (правый верхний угол) по умолчанию снят.
При его включении становятся доступными **«Очистить БД»**, **«Выгрузить CSV»**
и вкладка **«Параметры»**.
При отключении эти элементы скрываются. Состояние сбрасывается при каждой
перезагрузке страницы.

### 2.6. Параметры (config_service.yaml)

Во вкладке «Параметры» открывается JSON-редактор параметров сервиса. Изменения
сохраняются кнопкой **«Сохранить»** и применяются **при следующем запуске парсера**.
Секреты (токены ботов) через интерфейс не редактируются — они задаются переменными
окружения (`ZAKUPKI_TELEGRAM_TOKEN`, `ZAKUPKI_MAX_TOKEN`, `ZAKUPKI_MAX_CHAT_ID` и т.п.).

## 3. Команды командной строки

Все команды запускаются через `uv run zp --configs configs …` (короткое имя `zp`;
длинное `zakupki-parser` доступно как алиас).

| Команда | Назначение |
|---|---|
| `zp check-config` | Проверка конфигурации и вывод её параметров (без обращения к БД) |
| `zp run-once` | Один проход по всем включённым площадкам |
| `zp run-service` | Периодический запуск по таймеру (`timeout_seconds` из `config_ops.yaml`) |
| `zp stop [--force]` | Остановка запущенных процессов парсера (мягко, затем принудительно) |
| `zp serve` | Запуск веб-интерфейса и REST API |
| `zp capture-fixture --platform <id>` | Сохранение HTML-фикстур страниц для разработки/тестов |

## 4. Уведомления

Парсер может уведомлять о новых закупках через **Telegram**, **MAX** или
**webhook** — настраивается в `config_ops.yaml → notifications`
(`backend: telegram | max | webhook`). Уведомление отправляется для новых закупок
после расчёта скоринга — **после каждой стадии каскада** (fit/pwin/margin), если
результат стадии прошёл её порог (`notify_min_fit_score`/`notify_min_pwin`/
`notify_min_margin` в `config_ops.yaml`). Подробнее: `docs/telegram-subscriber.md`,
`docs/max-subscriber.md`.

## 5. Частые вопросы

**После запуска парсера список не обновился.**
Запуск сбора выполняется в том же процессе, что и веб-интерфейс; обновление
происходит по WebSocket автоматически. Если сервис запущен со старой версией
кода — перезапустите `uv run zp serve` и обновите страницу.

**Поле ИНН у заказчика пустое.**
ИНН извлекается со страницы организации (mos.ru, ЕИС, ЭТП). Если страница изменилась
и извлечение не сработало, ИНН остаётся пустым (nullable) — закупка при этом
сохраняется.

**Где хранятся данные?**
В PostgreSQL: таблица закупок `procurements` и справочники `customers`,
`platforms`, `procedure_types`, `procedure_type_mappings`. Схема поддерживается
миграциями Liquibase, которые применяются автоматически при старте.

**Что делать при сбое сбора на одной площадке?**
Сбой одной площадки не останавливает остальные; он учитывается в
circuit-breaker'е для вежливой деградации и логируется. Ошибки доступны в
файле лога (`data/parser.log`).
