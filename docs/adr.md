# Архитектурные решения (ADR)

Здесь фиксируются ключевые архитектурные решения парсера площадок закупок.
Формат каждой записи: контекст, решение, последствия.

---

## ADR-1. Все селекторы DOM выносятся в конфигурацию

**Статус:** принято.

**Контекст.**
Парсер работает с внешними площадками (zakupki.mos.ru, ЕИС, ЭТП), чья разметка —
это SPA со «хешированными» CSS-классами (styled-components) и позиционными полями.
Разметка может меняться при каждом деплое, а площадок — несколько. Зашитые в код
селекторы пришлось бы править в коде и перевыпускать релиз при каждом изменении DOM.

**Решение.**
Все селекторы (контейнеры карточек, поля списка/деталей, элементы файлов, панель
сортировки и фильтров, порядок позиционных полей) задаются исключительно в
`config_dom.yaml` (и связанных блоках). Код не содержит селекторов: движок читает
их из конфига через pydantic-модели, поддерживает `index` (N-й элемент) и
regex-обработчики для позиционных полей.

**Последствия.**
- Изменение разметки площадки — правка только YAML, без изменения кода и релиза.
- Добавление новой площадки — новый блок в `config_dom.yaml`.
- Риск: некорректный селектор обнаруживается на прогоне, поэтому конфиг валидируется
  на старте (`check-config`), а извлечение покрыто тестами на HTML-фикстурах.

## ADR-2. Фильтрация — через параметры запроса, если платформа их поддерживает

**Статус:** принято.

**Контекст.**
Для отбора закупок площадки предлагают два способа: (а) клики по панели фильтров
(скрытые/аккордеонные контролы, сложные для headless-автоматизации) и (б) URL-запрос
с параметрами (например, `zakupki.mos.ru/purchase/list?...filter=<json>`). Панель
фильтров в headless-режиме открывается нестабильно и добавляет много шагов/запросов.

**Решение.**
Если платформа предусматривает фильтрацию через параметры запроса — использовать их
(блок `search` в `config_dom.yaml`: имена параметров, JSON-структуры `filter`/`state`,
плейсхолдеры дат). DOM-шаги (`filters`) остаются как механизм для площадок, где
URL-фильтрации нет. Маппинг полностью конфигурируем: и имена параметров, и структуры
JSON, и формат дат задаются в конфиге.

**Последствия.**
- Быстрее и надёжнее: один GET вместо серии кликов; меньше запросов к площадке
  (важно для антиблока).
- Сортировка по дате публикации задаётся тем же механизмом (порядок фиксирован —
  `publication_date_desc`).
- Ограничение: способ зависит от платформы; для площадок без URL-фильтров применяются
  DOM-шаги.

## ADR-3. Скоринг закупки: несколько способов заполнения, предпочтителен воркер

**Статус:** принято (детали вызова внешнего сервиса требуют согласования при
включении парсера в общую архитектуру).

**Контекст.**
Каждой закупке требуется скоринг `Score = Fit(ОКПД2) × P(win) × Margin`. Способов
несколько, и у каждого свои риски:
1. Внутренняя эвристика (таблица fit по ОКПД2, Margin = НМЦК) — быстра, но груба.
2. Вызов внешнего сервиса перед записью закупки в БД — задерживает фиксацию «сырой»
   информации с ЭТП и добавляет запросов к площадке на критическом пути.
3. Отдельный асинхронный воркер — обрабатывает записи после сохранения.
4. Внешний сервис сам пишет score через API (по своей инициативе).

Адекватный скоринг может требовать языковых моделей (LLM): это медленно, а также
связано с рисками «галлюцинаций» и отказов сервиса. Встраивать такие вызовы в
критический путь парсинга рискованно: парсер должен как можно быстрее и надёжнее
сохранить «сырую» информацию с ЭТП, не делая лишних запросов (во избежание блокировки
IP). Кроме того, сервис парсера должен полностью отвечать за заполнение своей БД,
поэтому заполнение score «по инициативе внешнего сервиса» менее предпочтительно.

**Решение.**
Реализованы несколько вариантов (`config_score.yaml -> method`/`external_call_mode`),
предпочтительным считается вариант с отдельным воркером:

- `method: default` — внутренняя эвристика при сохранении (`score_method=default`);
- `method: external` + `external_call_mode: worker` — **предпочтительно**: парсер
  сохраняет запись с начальным (default) score, а отдельный воркер (`score-worker`/шаг
  цикла) проходит по записям со `score_method=default`, ставит `score_method=calculating`
  (чтобы не вызывать внешний сервис повторно), вызывает внешний сервис и обновляет score;
- `method: external` + `external_call_mode: before_save` — вызов внешнего сервиса перед
  записью (запасной вариант; при ошибке — fallback на default);
- внешний сервис может сам обновить score через `POST /api/procurements/{id}/score`
  (менее предпочтительно, но предусмотрено).

Просроченный срок подачи заявок всегда даёт `score = 0`,
`score_method = deadline_expired` — независимо от выбранного способа.

**Последствия.**
- «Сырые» данные с ЭТП сохраняются максимально быстро; скоринг не задерживает парсинг.
- Внешний сервис изолирован: сбои/галлюцинации LLM не ломают сбор данных.
- `calculating` защищает от повторных вызовов внешнего сервиса.
- Требует согласования при интеграции в общую архитектуру (какой вариант использовать,
  адрес внешнего сервиса, формат payload) — поэтому параметры вынесены в `config_score.yaml`
  и могут быть изменены без изменения кода.

## ADR-4. Таблица закупок временно остаётся ненормализованной

**Статус:** принято (нормализация отложена).

**Контекст.**
Данные закупок хранятся в одной таблице `procurements`: часть полей — это
«сырые» значения с площадки (например, коды ОКПД2/КПГЗ строкой через запятую,
`files_json`, `detail_json`), а не ссылки на справочники. Полноценная нормализация
предполагает создание справочных таблиц (площадки, заказчики, коды ОКПД2/КПГЗ и т.п.), 
причём эти же справочники будут использоваться сервисами расчёта
скора (фильтрация по тематике, fit-таблицы, внешний скоринг).

**Решение.**
На текущем этапе таблица `procurements` остаётся ненормализованной: значения хранятся
в удобной для записи и чтения форме, а необходимые для скоринга данные (коды ОКПД2,
заказчик, предмет) дублируются в отдельных колонках для быстрых запросов. Нормализация
(выделение справочников) откладывается до момента перехода к разработке сервисов
расчёта скора, которые будут использовать эти справочники.

**Последствия.**
- Быстрая запись и чтение «сырых» данных; меньше JOIN-ов при выгрузке/отчётах.
- Избыточность хранимых данных (например, коды ОКПД2 и в колонке, и в `detail_json`);
  контролируется на уровне приложения (уникальность `number + source_platform`).
- При переходе к скоринговому сервису — выделение справочников и миграция данных
  (новые Liquibase-чанги); обратная совместимость через `detail_json`.

## ADR-5. Обработка файлов (в т.ч. ТЗ внутри ZIP) — внешним сервисом

**Статус:** принято.

**Контекст.**
Парсер в основном режиме не скачивает файлы — только сохраняет их имена и URL
(`files_json`), а ТЗ — в два выделенных поля. Обнаружен кейс, когда техническое
задание лежит **внутри ZIP-архива** (имя архива не содержит «техническое задание»):
по имени файла такое ТЗ парсер определить не может.

**Решение.**
Парсер **не** вникает в содержимое архивов: он хранит только метаданные файлов
(`files_json`, включая ZIP), а распаковку ZIP и поиск ТЗ внутри выполняет
**внешний сервис обработки файлов**. Внешний сервис возвращает уточнённые
метаданные ТЗ через API (`POST /api/procurements/{id}/technical-spec`), и парсер
записывает их в `technical_spec_name/url/key`. Глубокая обработка контента
(PDF/DOCX) также остаётся за внешним сервисом. Контракт взаимодействия описан
в `docs/external-service-contract.md`.

**Последствия.**
- Парсер не усложняется ZIP-логикой; сохраняется «метаданный» режим.
- Поля `technical_spec_*` для ZIP-кейса заполняются внешним сервисом (асинхронно).
- Требуется контракт API (эндпоинт `technical-spec`) и согласование форматов — см.
  контракт.
