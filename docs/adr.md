# Архитектурные решения (ADR)

Здесь фиксируются ключевые архитектурные решения парсера площадок закупок.
Формат каждой записи: контекст, решение, последствия.

---

## ADR-1. Все селекторы DOM выносятся в конфигурацию

**Статус:** принято.

**Контекст.**
Парсер работает с внешними площадками (zakupki.mos.ru, ЕИС, ЭТП), чья разметка —
это SPA со «хешированными» CSS-классами (styled-components) и позиционными полями.
Разметка может меняться при каждом деплое, а площадок — несколько. Зашитые в код
селекторы пришлось бы править в коде и перевыпускать релиз при каждом изменении DOM.

**Решение.**
Все селекторы (контейнеры карточек, поля списка/деталей, элементы файлов, панель
сортировки и фильтров, порядок позиционных полей) задаются исключительно в
`configs/dom/<platform_id>.yaml` (и связанных блоках). Код не содержит селекторов: движок читает
их из конфига через pydantic-модели, поддерживает `index` (N-й элемент) и
regex-обработчики для позиционных полей.

**Последствия.**
- Изменение разметки площадки — правка только YAML, без изменения кода и релиза.
- Добавление новой площадки — новый файл в `configs/dom/<platform_id>.yaml`.
- Риск: некорректный селектор обнаруживается на прогоне, поэтому конфиг валидируется
  на старте (`check-config`), а извлечение покрыто тестами на HTML-фикстурах.

## ADR-2. Фильтрация — через параметры запроса, если платформа их поддерживает

**Статус:** принято.

**Контекст.**
Для отбора закупок площадки предлагают два способа: (а) клики по панели фильтров
(скрытые/аккордеонные контролы, сложные для headless-автоматизации) и (б) URL-запрос
с параметрами (например, `zakupki.mos.ru/purchase/list?...filter=<json>`). Панель
фильтров в headless-режиме открывается нестабильно и добавляет много шагов/запросов.

**Решение.**
Если платформа предусматривает фильтрацию через параметры запроса — использовать их
(блок `search` в `configs/dom/<platform_id>.yaml`: имена параметров, JSON-структуры `filter`/`state`,
плейсхолдеры дат). DOM-шаги (`filters`) остаются как механизм для площадок, где
URL-фильтрации нет. Маппинг полностью конфигурируем: и имена параметров, и структуры
JSON, и формат дат задаются в конфиге.

**Последствия.**
- Быстрее и надёжнее: один GET вместо серии кликов; меньше запросов к площадке
  (важно для антиблока).
- Сортировка по дате публикации задаётся тем же механизмом (порядок фиксирован —
  `publication_date_desc`).
- Ограничение: способ зависит от платформы; для площадок без URL-фильтров применяются
  DOM-шаги.

## ADR-3. Скоринг закупки: асинхронное обращение к микросервису после сохранения записи

**Статус:** принято (детали вызова микросервиса требуют согласования при включении
парсера в общую архитектуру).

**Контекст.**
Каждой закупке требуется скоринг `Score = Fit(ОКПД2) × P(win) × Margin` (см. ADR-6).
Рассматривались варианты:
1. Внутренняя эвристика при сохранении — быстра, но груба: не учитывает компетенции
   поставщика и рейтинг заказчика.
2. Вызов внешнего сервиса перед записью — задерживает фиксацию «сырых» данных с ЭТП
   и добавляет запросы на критическом пути парсинга.
3. Отдельный асинхронный воркер — дополнительный компонент, усложняет эксплуатацию.
4. Внешний сервис сам пишет score через API — парсер не гарантирует, что подписчик
   получит закупку с финальным скорингом.

Адекватный скоринг требует языковых моделей (LLM) и анализа компетенций поставщика:
это медленно и связано с рисками отказов. Встраивать такие вызовы в критический путь
парсинга рискованно: парсер должен как можно быстрее и надёжнее сохранить «сырую»
информацию с ЭТП, не делая лишних запросов (во избежание блокировки IP). При этом
подписчик должен получать закупку уже с финальным скорингом, а не с предварительным.

**Решение.**
Скоринг выполняется микросервисом скоринга асинхронно, после сохранения «сырой» записи:

1. Парсер сохраняет запись закупки в БД максимально быстро — с начальным (default)
   скорингом (`score_method=default`, см. ADR-6) и без ожидания внешних вызовов.
2. Сразу после сохранения парсер отправляет микросервису скоринга асинхронный запрос
   (вызов или постановка в очередь).
3. Микросервис получает **сырую запись закупки** и **текст с описанием компетенций
   поставщика**, а также использует собственную базу данных о заказчиках; согласование
   заказчиков между микросервисом и парсером — см. ADR-4.
4. Микросервис возвращает оценку; парсер обновляет score записи в БД.
5. **Оповещение подписчиков выполняется только после прихода нового скора и обновления
   записи в БД** — подписчик видит закупку с финальной оценкой.

Просроченный срок подачи заявок всегда даёт `score = 0`, `score_method = deadline_expired` —
независимо от микросервиса.

**Последствия.**
- «Сырые» данные с ЭТП фиксируются максимально быстро; скоринг не задерживает парсинг.
- Микросервис изолирован: сбои/«галлюцинации» LLM не ломают сбор данных.
- Оповещения всегда содержат финальный score (не предварительный).
- Парсер полностью отвечает за наполнение своей БД; микросервис — только источник оценки.
- Требует согласования контракта вызова (адрес, формат payload, способ доставки —
  синхронный вызов или очередь) при интеграции в общую архитектуру. Способ доставки:
  на старте — очередь-«outbox» на базе PostgreSQL (таблица `scoring_jobs`, потребление
  воркером `score-worker`) для атомарности с транзакцией записи и идемпотентных ретраев;
  при появлении нескольких потребителей — переключение на брокер сообщений
  (RabbitMQ / Kafka / NATS).

## ADR-4. Нормализация таблицы закупок: заказчики — в отдельной таблице

**Статус:** принято (требует миграции, инкрементального наполнения справочника,
эндпойнта рейтинга и согласования сопоставления заказчиков между сервисами).

**Контекст.**
Данные закупок хранятся в одной таблице `procurements`; заказчик хранится строкой
и дублируется в каждой записи. Для дефолтного скоринга нужна оценка вероятности
победы `P(win)`, определяемая рейтингом заказчика (см. ADR-6) — держать этот рейтинг
в каждой записи закупки нельзя. При этом исторические данные о закупках заказчика
**вне зоны ответственности парсера**: их ведут другие микросервисы (например,
микросервис скоринга).

**Решение.**
- Заказчики выносятся в отдельную таблицу `customers`: идентификатор, наименование,
  ИНН (если доступен в карточке закупки — на ЕИС он есть, на mos.ru нет), **рейтинг**
  (`rating`), `created_at`/`updated_at`. Историю закупок парсер не хранит.
- Таблица заполняется **инкрементально**: при сохранении очередной закупки парсер
  сопоставляет заказчика с записью `customers`; если заказчика ещё нет — создаёт новую
  запись. Справочник пополняется по мере появления заказчиков в закупках.
- `procurements` ссылается на `customers` внешним ключом (`customer_id`).
- **Рейтинг заказчика заполняется через отдельный эндпойнт сервиса парсера**
  (например, `POST /api/customers/{id}/rating`), который вызывают другие сервисы
  (в т.ч. микросервис скоринга). Парсер не вычисляет рейтинг самостоятельно.

**Согласование заказчиков между сервисами.**
Разные сервисы идентифицируют заказчика по-разному (варианты написания наименования,
наличие/отсутствие ИНН, отсутствие общего идентификатора). Для сопоставления:
- ИНН доступен не на всех площадках (на ЕИС — есть, на mos.ru — только
  наименование), поэтому основной ключ сопоставления — нормализованное наименование,
  а ИНН — уточняющий атрибут там, где он есть;
- парсер предоставляет API со списком заказчиков, чтобы другие сервисы могли
  выполнить сопоставление своих данных с `customers`;
- при невозможности однозначного сопоставления допускаются дублирующие записи
  с последующим склеиванием (вручную или отдельным сервисом).

**Последствия.**
- Рейтинг заказчика хранится централизованно и обновляется через API парсера;
  дефолтный скоринг берёт `P(win)` из него (см. ADR-6).
- Парсер хранит только справочную информацию о заказчике и его рейтинг — без истории
  закупок.
- Проблема согласования заказчиков между сервисами решается через ИНН/нормализованное
  имя и API-список; остаётся риск дубликатов при неоднозначном сопоставлении.
- Требуются миграция данных, инкрементальное наполнение справочника и эндпойнт рейтинга.

## ADR-5. Обработка файлов (в т.ч. ТЗ внутри ZIP) — внешним сервисом

**Статус:** принято.

**Контекст.**
Парсер в основном режиме не скачивает файлы — только сохраняет их имена и URL
(`files_json`), а ТЗ — в два выделенных поля. Обнаружен кейс, когда техническое
задание лежит **внутри ZIP-архива** (имя архива не содержит «техническое задание»):
по имени файла такое ТЗ парсер определить не может.

**Решение.**
Парсер **не** вникает в содержимое архивов: он хранит только метаданные файлов
(`files_json`, включая ZIP), а распаковку ZIP и поиск ТЗ внутри выполняет
**внешний сервис обработки файлов**. Внешний сервис ищет ТЗ по метаданным
(`files_json`), скачивает и обрабатывает его. Глубокая обработка контента
(PDF/DOCX) также остаётся за внешним сервисом. Контракт взаимодействия описан
в `docs/external-service-contract.md`.

**Последствия.**
- Парсер не усложняется ZIP-логикой; сохраняется «метаданный» режим (все файлы,
  включая ТЗ, в `files_json`).
- ТЗ для ZIP-кейса находит внешний сервис (асинхронно) по имени файла в архиве.

## ADR-6. Дефолтная оценка скоринга (Score = Fit × P(win) × Margin)

**Статус:** принято.

**Контекст.**
Каждой закупке нужна числовая оценка привлекательности. Микросервис скоринга (ADR-3)
использует LLM и собственные данные, но парсер должен работать и без него: пока
микросервис не ответил (или недоступен), в БД лежит дефолтная оценка. Формула и
источники её компонент должны настраиваться без изменения кода.

**Решение.**
Дефолтная оценка: `Score = Fit × P(win) × Margin`, где:
- **Fit** — соответствие закупки тематике; оценивается по коду ОКПД2 с использованием
  коэффициентов из конфига (`config_score.yaml`, fit-таблица ОКПД2). Если код отсутствует
  в таблице — применяется коэффициент по умолчанию.
- **P(win)** — вероятность победы; определяется рейтингом заказчика из таблицы
  `customers`, который заполняется через эндпойнт парсера (см. ADR-4). Если рейтинг
  неизвестен — значение по умолчанию из конфига.
- **Margin** — маржа; вычисляется как норма прибыли из конфиг-файла, применённая
  к НМЦК закупки.

Просроченный срок подачи заявок всегда даёт `score = 0` (`score_method = deadline_expired`).
Дефолтная оценка помечается `score_method = default`; при ответе микросервиса она
заменяется внешней (ADR-3).

**Последствия.**
- Расчёт предсказуем и полностью настраивается конфигами (fit-коэффициенты, рейтинг
  заказчика, норма прибыли) без изменения кода.
- Парсер работоспособен без микросервиса: каждая запись сразу получает осмысленную
  дефолтную оценку.
- Качество оценки зависит от полноты fit-таблиц, актуальности рейтинга заказчика
  и корректности нормы прибыли.
- Внешний скоринг переопределяет дефолт; различия фиксируются в `score_method`.

## ADR-7. Внешний скоринг через транспорт + Redis-очередь; авто-пуш и пороговое уведомление

**Статус:** принято, реализовано. Конвейер `scoring_transport` + `scoring_service` + Redis,
авто-пуш из парсера, возврат через `POST /score` и постадийное пороговое уведомление
работают. LLM-пайплайн `scoring_service` (Fit → Judge → refine →
уточнение по ТЗ) включён и работает **без заглушки** (`score_use_stub=false`), дополнен
веткой векторной близости Giga Embedder (с ADR-8 — как предварительным фильтром перед LLM).
Стадии P(win)/Margin вынесены в отдельные сервисы каскада (см. ADR-9).

**Контекст.**
ADR-3 изначально фиксировал очередь-«outbox» на базе PostgreSQL (таблица `scoring_jobs`,
потребление воркером `score-worker`). На практике построен конвейер **`scoring_transport`
(gateway) + `scoring_service` (LLM-скоринг) + Redis** (ZSET `scoring:jobs`, LIST
`scoring:results`). При этом в коде остались два параллельных пути внешнего скоринга:
встроенный прямой путь парсера (`ExternalScoreClient` при `before_save`/`worker`,
`Scheduler.run_scoring_worker`) и конвейер через транспорт. Эвристика дефолтного score
(ADR-6) продублирована в трёх местах (парсер, транспорт, конфиг), а уведомления подписчиков
отправляются при парсинге без порога — до прихода финального внешнего скора.

**Рассмотренные альтернативы.**
1. **Прямой HTTP-вызов скоринга из парсера** (`before_save`, синхронно до записи) —
   задерживает фиксацию «сырых» данных и добавляет запросы на критическом пути парсинга
   (риск блокировки IP). Отклонено для внешнего скоринга.
2. **Очередь-«outbox» на PostgreSQL** (первоначальная формулировка ADR-3) — атомарна с
   транзакцией записи, но связывает очередь с БД парсера и требует воркера на стороне
   парсера; заменено выделенным Redis-транспортом.
3. **Брокер сообщений (RabbitMQ / Kafka / NATS)** — избыточен при единственном
   потребителе; оставлен как направление развития при росте числа потребителей.
4. **Сервис скоринга сам пишет score в БД парсера напрямую** — нарушает принцип единой
   границы: парсер остаётся единственным владельцем своей БД (см. ADR-3/ADR-4).

**Решение.**
Канонический внешний скоринг — конвейер **транспорт + Redis + сервис скоринга**, с
автоматической подачей заданий из парсера и пороговым уведомлением:

1. **Авто-пуш (после сохранения).** Парсер максимально быстро сохраняет «сырую» запись с
   дефолтным скорингом (`score_method=default`, ADR-6), затем отправляет в транспорт
   `POST /api/scoring/jobs {procurement_id, priority=default_score}`. Это связывает парсер
   с конвейером автоматически (без ручного ingest).
2. **Постановка в очередь по скору.** Транспорт кладёт задачу в Redis ZSET `scoring:jobs`
   (`member = proc:{id}`, `score = priority = default_score`) — приоритет отражает
   «ожидаемую ценность» закупки. Приоритет приходит из парсера, поэтому транспорт **не
   пересчитывает** дефолтный score по собственной fit-таблице (устраняет дублирование
   эвристики ADR-6).
3. **Потребление задания.** `scoring_service` берёт самое приоритетное задание **напрямую
   из Redis** через `ZPOPMAX` (не запрашивая транспорт по HTTP): транспорт отвечает только
   за ingest и возврат результата, а не за раздачу заданий. Надёжность — TTL-аренда
   `scoring:processing` + `recover_stale` (возврат «зависших» задач); идемпотентность
   гарантируется перезаписью через `POST /score`.
4. **Возврат результата.** Сервис публикует результат в `scoring:results` (`LPUSH`);
   транспорт (`BRPOP`) получает его и возвращает в парсер через
   `POST /api/procurements/{id}/score` (с ретраями/backoff). Транспорт — **единственная
   граница** между конвейером и парсером (симметрия, центральные ретраи/авторизация/
   наблюдаемость).
5. **Запись и пороговое уведомление.** Парсер обновляет score и результат стадии в БД
   (`repository.update_score`), затем в обработчике `POST /score` сравнивает возвращаемое
   значение стадии с её порогом (`notify_min_fit_score`/`notify_min_pwin`/
   `notify_min_margin` из `config_ops.yaml`) и уведомляет подписчиков **только** если порог
   пройден. Уведомление, т.о., **откладывается** до прихода результата стадии внешнего
   скоринга (вместо отправки при парсинге без порога). Каскад стадий и постадийные
   уведомления — ADR-9.
6. **Упрощение.** Встроенные прямые пути внешнего скоринга (`ExternalScoreClient` при
   `before_save`/`worker`, `Scheduler.run_scoring_worker`) и дублирующая fit-таблица
   транспорта удалены.

**LLM-пайплайн `scoring_service`** (`scoring_service/scoring.py`): Fit (0–10, reasoning +
`fit_score`) → Judge (критики / verdict / `final_fit_score`) → при `verdict=reject` до
`num_refine_rounds` повторный Fit → уточнение по тексту ТЗ (`tz_review`, флаги
`requires_tz_review`/`requires_tz_body`) → ветка Giga Embedder (косинусная близость,
`giga_embedding_alpha`, результат `embedding_similarity`; с ADR-8 — предварительный
фильтр перед LLM). Score = нормализованный Fit × P(win) × Margin.

**Последствия.**
- Единая, симметричная граница: парсер взаимодействует с конвейером только через транспорт
  (ingest и возврат результата); `scoring_service` не имеет доступа к БД парсера.
- Подписчики получают уведомления только после результата стадии каскада, прошедшего
  её порог (постадийно, ADR-9).
- Парсер продолжает работать без конвейера: каждая запись сразу получает дефолтный score;
  при недоступности конвейера внешний score просто не придёт (и уведомление по внешнему
  скорингу не отправится).
- Устраняется дрейф конфигурации fit-таблицы (единственный источник — `config_score.yaml`).
- Требуются: реализация авто-пуша и порога `notify_min_fit_score` (выпил deprecated-путей
  выполнен).

## ADR-8. Предварительная фильтрация закупок по векторной близости перед LLM-скорингом

**Статус:** принято, реализовано. Ветка Giga Embedder в `scoring_service` выполняется
до LLM-пайплайна; при близости ниже порога `embedding_filter_threshold` (0.66) LLM не
вызывается, возвращается `fit_score=0`, `score=0` и `score_method=sim`.

**Контекст.**
LLM-скоринг (ADR-7) — дорогой по времени и ресурсам: на каждую закупку выполняется
Fit → Judge → refine → (уточнение по ТЗ). Значительная часть поступающих закупок
нерелевантна компетенциям поставщика, и обрабатывать их полным пайплайном затратно.
Требуется дешёвый предварительный фильтр, который отсекает заведомо нерелевантные
закупки до запуска LLM.

Рассматривались способы предварительного отбора по доступным в карточке признакам:
1. **Фильтрация по ключевым словам** — результаты сильно сужаются: закупка не содержит
   точных ключевых фраз, но описывает ту же суть синонимичными терминами (например,
   «внедрение программного обеспечения» вместо «автоматизация»). Отсеивается и релевантное.
2. **Фильтрация по кодам ОКПД2** — наоборот, слишком грубая: коды покрывают широкие
   категории, и по коду проходит много «мусора» — закупок, формально попадающих в класс,
   но не относящихся к тематике поставщика.

**Решение.**
Использовать **векторную близость** эмбеддингов описания закупки и текста компетенций
поставщика (косинусная близость, Giga Embedder). Близость вычисляется до LLM-пайплайна;
если она ниже порога `embedding_filter_threshold` из конфига (`config.yaml`, по умолчанию
0.66) — закупка отсекается без вызова LLM (результат: `fit_score=0`, `score=0`,
`score_method=sim`).

Векторная близость объединяет сильные стороны обоих подходов и компенсирует их
недостатки:
- при отборе по кодам ОКПД2 она отсеивает «мусор» — закупки, формально попавшие в класс
  кода, но не относящиеся к тематике;
- при отборе по ключевым словам она ловит синонимичную близость и при этом отсеивает
  «false-friend»-случаи, где термины совпадают, а смысл разный: например, закупка
  «искусственной ели» не проходит по запросу «искусственный интеллект».

**Выбор порога.**
Порог 0.66 выбран эмпирически на выборке из 150 закупок, отсортированных по векторной
близости. В качестве порога взята минимальная близость 0.6613, округлённая до двух знаков
после запятой: ниже неё в выборке нет закупок с `fit_score > 0.8`. Исключение — одна
закупка, для которой LLM ошибочно присвоила высокое значение `fit_score`, что не меняет
общую границу отсечения.

**Последствия.**
- Существенная экономия: нерелевантные закупки не проходят дорогой LLM-пайплайн и
  уточнение по ТЗ; нагрузка на LLM и латентность конвейера снижаются.
- Фильтрация терминальна для каскада скоринга: результат `score_method=sim` не
  запускает переходы Fit → P(win) → Margin, уведомления подписчиков не отправляются
  (`fit_score=0` ниже порога `notify_min_fit_score`).
- Порог настраивается в конфиге (`embedding_filter_threshold`); значение `<= 0` отключает
  фильтрацию. Требуется настроенный ключ доступа Giga: без ветки эмбеддингов фильтрация
  не выполняется (сбой ветки также не роняет скоринг — закупка обрабатывается как раньше).
- Порог подобран на ограниченной выборке и должен уточняться по мере накопления данных;
  риск — как ложное отсечение релевантных закупок, так и пропуск «мусора» при снижении порога.

## ADR-9. Каскад скоринга Fit → P(win) → Margin (отдельные сервисы стадий)

**Статус:** принято, реализовано. Стадии **P(win)** (`pwin_service`) и **Margin**
(`margin_service`) развёрнуты как отдельные сервисы с общим кодом `scoring_common`;
переходы между стадиями оркестрирует парсер по порогам; уведомления отправляются
после каждой стадии с порогом по возвращаемому значению стадии. Стадия P(win) пока
работает в режиме заглушки (`use_stub=true`, P(win) = константа 0.5) — модель
коэффициентов калибруется (TODO).

**Контекст.**
По ADR-6/ADR-7 score = Fit × P(win) × Margin, но стадии P(win) и Margin были
заглушками: P(win)=1, Margin = НМЦК × margin_rate — вычислялись в парсере как часть
дефолтной эвристики. Внешний скоринг (ADR-7) выполнял только стадию Fit (LLM),
а итог по формуле считался как Fit × константа. Подписчики уведомлялись один раз —
по итоговому `fit_score`. Для адекватной оценки закупки требуются независимые стадии
P(win) (рейтинг/квалификация заказчика, категории закупки) и Margin (норма прибыли),
которые меняются независимо от Fit.

**Рассмотренные альтернативы.**
1. **Считать все три множителя внутри `scoring_service`** (один LLM-сервис) — сервис
   становится толстым, стадии не масштабируются независимо, формулы P(win)/Margin
   не переиспользуются.
2. **Считать P(win)/Margin в парсере** (эвристика) — возврат к ADR-6-заглушкам: без
   отдельных сервисов нет данных о заказчике/категориях и нет независимого развития.
3. **Каскад без флагов включения** (`pwin_enabled`/`margin_enabled`) — при развёртывании
   новых стадий парсер либо теряет задачи (очередь без воркера), либо должен
   перезапускаться синхронно с сервисами.

**Решение.**
Внешний скоринг — **каскад из трёх независимых стадий**, соединённых Redis-очередями:

1. **Fit** (`scoring_service`) — LLM-пайплайн (ADR-7/ADR-8), возвращает `fit_score` (0..1)
   и `score_method=fit`. Результат публикуется в `scoring:results`, транспорт возвращает
   его в парсер через `POST /score`.
2. **P(win)** (`pwin_service`) — потребляет очередь `pwin:jobs`, считает
   `P(win) = base_pwin × k_smp × k_license × k_large × k_procedure × k_ai`
   (формула и коэффициенты — в `scoring_common/pwin.py`, YAML-источник в конфиге
   сервиса), возвращает `p_win` и `score_method=pwin`. Сейчас используется
   заглушка `use_stub=true` (P(win) = константа `stub_pwin`) до калибровки
   коэффициентов модели.
3. **Margin** (`margin_service`) — потребляет очередь `margin:jobs`, считает
   `Margin = НМЦК × margin_rate`, возвращает `margin` и `score_method=margin`.

**Оркестрация — парсером** (обработчик `POST /api/procurements/{id}/score`):
- транспорт маршрутизирует задания по параметру `stage` в
  `POST /api/scoring/jobs {procurement_id, priority, stage}` в очередь стадии
  (`scoring:jobs`/`pwin:jobs`/`margin:jobs`); транспорт — единственная граница
  между каскадом и парсером (ADR-7);
- после записи результата стадии парсер сравнивает **возвращаемое значение стадии**
  (не произведение score) с порогом следующей: `fit_score ≥ pwin_fit_threshold` →
  очередь P(win); `p_win ≥ margin_pwin_threshold` → очередь Margin; стадия Margin —
  финальная. Стадии включаются флагами `pwin_enabled`/`margin_enabled`
  (`config_score.yaml`) — безопасный ролл-аут без потери задач;
- каждый множитель сохраняется отдельной колонкой (`fit_score`, `p_win`, `margin`,
  миграция Liquibase 1.19); `score` — накопленное произведение
  (после финальной стадии = fit × p_win × margin); `score_method` принимает значения
  `fit`/`pwin`/`margin` (миграция 1.19 также переименовала `external` → `fit`).

**Уведомления — после каждой стадии.** Подписчик получает карточку с результатом
стадии, если стадия уведомления включена (`notify_fit_enabled`/`notify_pwin_enabled`/
`notify_margin_enabled`) и возвращаемое значение стадии прошло её порог
(`notify_min_fit_score`/`notify_min_pwin`/`notify_min_margin`; 0 — порог отключён).
Уведомление отправляется только при **изменении** результата стадии (не при повторной
доставке). При недоступности следующей стадии парсер делает fallback: каскад
останавливается, уведомление отправляется на терминальной стадии.

**Общий код стадий** вынесен в `scoring_common`: параметризованная Redis-очередь
(`queue.py`), клиент API парсера (`parser_api.py`), формула P(win) (`pwin.py`),
маржа (`margin.py`), цикл воркера (`stage_worker.py`). `scoring_service` и
`scoring_transport` мигрированы на общий код.

**Последствия.**
- Стадии независимы: масштабируются и развиваются по отдельности; P(win)/Margin
  могут использовать данные заказчика/категорий без изменения парсера.
- Парсер остаётся единственным владельцем БД и оркестратором каскада (переходы,
  пороги, уведомления) — симметрия ADR-7 сохраняется.
- Три множителя видны по отдельности в БД и API (прозрачность скоринга для аналитика).
- Постадийные уведомления: подписчик получает закупку уже после стадии Fit, а не ждёт
  завершения всего каскада.
- Требуется согласование порогов и коэффициентов P(win)/Margin по мере накопления
  данных (калибровка); риск — неверно подобранные пороги переходов отсекают закупки
  от стадий P(win)/Margin или гонят «мусор» через LLM.
